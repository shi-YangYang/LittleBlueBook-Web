## 1. 背景

SPEC-007 已建立一级文字评论、笔记点赞、收藏和关注，SPEC-009 已建立互动通知中心。当前用户不能回复其他评论、不能点赞评论，笔记没有真实浏览量，用户之间也没有私信通道。

本 Spec 扩展现有评论与通知模型，建立可验收的评论回复、评论点赞、有效笔记浏览量和一对一实时私信闭环。

## 2. 已确认目标

- 登录用户可以回复一级评论或其他回复；
- 评论只展示两级结构，回复其他回复时在同一一级评论下扁平展示；
- 登录用户可以点赞或取消点赞他人的一级评论和回复；
- 回复与评论点赞接入现有通知中心；
- 笔记展示基于真实有效访问的浏览量；
- 匿名浏览可以计数，但不保存 IP、User-Agent 或原始访客 Cookie；
- 互相关注的登录用户可以建立一对一纯文本私信会话；
- 私信通过 WebSocket 实时同步，PostgreSQL 是消息、会话和未读状态的唯一真实来源；
- WebSocket 不可用时仍可通过 HTTP 发送，重连后同步遗漏消息；
- 本期不使用 Redis 保存评论互动、浏览量、私信或未读状态。

## 3. 范围

### 3.1 本期包含

- 两级评论展示与扁平回复；
- 回复发布、分页、删除、定位和计数；
- 一级评论与回复的点赞、取消点赞和数量；
- 评论回复通知与评论点赞通知；
- 笔记有效浏览上报、`30` 分钟去重和权威总数；
- 登录用户和匿名浏览的隐私安全去重；
- 首页卡片、个人主页卡片和笔记详情浏览量展示；
- 一对一私信会话、历史消息、未读数和已读状态；
- `/messages` 会话页、左侧私信入口及他人公开主页私信入口；
- WebSocket 实时消息和已读回执；
- HTTP 发送、重连同步和幂等去重；
- 数据库迁移、OpenAPI、单元、集成、组件和 Browser E2E。

### 3.2 本期不包含

- 超过两级的可视嵌套评论树；
- 评论或回复编辑、媒体附件、富文本、置顶或热度排序；
- `@` 任意用户搜索和提及；
- 评论点赞用户列表；
- 对历史回复、评论点赞通知或笔记浏览量进行回填；
- 基于 IP、设备指纹或 User-Agent 的访客追踪；
- 精确的跨设备独立访客统计或数据分析看板；
- 陌生人私信、消息请求箱、群聊、在线状态或正在输入提示；
- 图片、视频、文件、语音或其他富媒体私信；
- 消息编辑、撤回、删除、转发、引用或表情反应；
- 会话删除、归档、置顶、免打扰、拉黑、举报和运营审核；
- 邮件、浏览器系统通知、移动推送或声音提醒；
- Redis Pub/Sub、Redis 缓存、消息队列、Outbox 或多实例 WebSocket 广播；
- 因评论、浏览或私信改变推荐排序；
- App 端。

## 4. 用户、认证与权限

- 未登录用户可公开阅读评论、回复、点赞数和浏览量；
- 未登录点击回复、评论点赞或私信时复用现有邮箱登录弹框；
- 登录后可恢复待执行的评论点赞意图；回复草稿保留但不自动发送；
- 直接访问 `/messages` 且未登录时打开登录弹框，登录成功后返回该页；
- 只有会话参与者可以读取该会话、消息和已读状态；
- 用户不能与自己建立私信会话；
- 发送每条私信时都必须在服务端重新确认双方互相关注；
- 取消互相关注后历史会话继续可读，但双方都不能发送新消息；
- 重新互相关注后原会话恢复发送，不创建重复会话。

## 5. 评论回复

### 5.1 层级和定位

- 可视结构只有“一级评论 → 回复列表”两级；
- 回复一级评论时，直接归属该一级评论；
- 回复其他回复时，仍归属同一一级评论，并展示“回复 @昵称”；
- 服务端必须验证被回复目标属于同一笔记和同一根评论；
- 删除的评论或回复不能接收新回复。

### 5.2 内容与排序

- 回复沿用评论纯文本规则：去除首尾空白后为 `1～500` 个 Unicode 字符；
- 不解析 HTML 或 Markdown，不接受媒体附件；
- 一级评论继续按 `createdAt DESC, id DESC` 稳定倒序；
- 同一一级评论下的回复按 `createdAt ASC, id ASC` 稳定正序；
- 一级评论每页 `20` 条；
- 每条一级评论默认展示最早 `3` 条有效回复或结构性占位；
- 展开后每次继续加载 `10` 条；
- 详情页“共 N 条评论”包含有效一级评论和有效回复，不包含已删除占位。

### 5.3 发布交互

- 点击“回复”后复用详情页底部评论输入区；
- 输入区显示“回复 @昵称”和取消回复操作；
- 取消后恢复为普通一级评论输入，已输入内容保留；
- 发送期间防止重复提交；
- 成功后把服务端返回的回复放入所属评论，同步回复数和评论总数；
- 失败时保留草稿、回复目标和现有列表；
- 会话失效时保留草稿并打开登录弹框，登录成功后不自动发送。

### 5.4 删除和占位

- 评论或回复作者可以删除自己的内容；
- 笔记作者可以删除自己笔记下任何评论或回复；
- 其他评论作者不能删除回复自己的他人内容；
- 删除前需要二次确认；
- 没有被可见回复引用的目标可以真实删除；
- 仍承载回复或被可见回复引用的目标保留结构性占位，只展示“该评论已删除”；
- 占位不显示原文、原作者私密信息、点赞按钮或点赞数；
- 删除时清除目标的评论点赞关系，有效评论总数减一；
- 占位下的其他有效回复继续显示。

## 6. 评论点赞

- 点赞对象包括有效一级评论和有效回复；
- 同一用户对同一目标最多存在一条有效点赞；
- 用户不能点赞自己的评论或回复；
- `PUT` 设置为已点赞，`DELETE` 设置为未点赞，两者均为幂等目标状态操作；
- 快速重复点击不得生成重复记录、负数或过期界面状态；
- 列表返回真实点赞数、当前用户是否已点赞及是否可点赞；
- 未登录可读数量，点击操作时进入登录流程；
- 界面可采用乐观更新，失败必须回滚到服务端确认状态。

## 7. 笔记浏览量

### 7.1 有效浏览

- 只有笔记详情已成功加载并在客户端展示后才发起浏览上报；
- 首页、频道、搜索或个人主页卡片曝光不计数；
- 笔记作者查看自己的笔记不计数；
- 同一登录用户对同一笔记在连续 `30` 分钟内最多计数一次；
- 同一匿名访客 Cookie 对同一笔记在连续 `30` 分钟内最多计数一次；
- 超过时间窗口后再次成功打开可以新增一次浏览；
- 上报失败不影响笔记正文、评论或其他互动的使用。

### 7.2 匿名访客隐私

- 服务端为没有访客标识的匿名浏览器生成高熵随机 Cookie；
- Cookie 使用 `HttpOnly`、`SameSite=Lax` 和与环境相符的 `Secure` 策略；
- 数据库只保存带服务端秘密的不可逆哈希或等价不可还原标识；
- 不保存 IP、User-Agent、屏幕指纹、硬件标识或原始 Cookie；
- Cookie 被禁用或写入失败时不得阻断页面，也不对用户展示技术错误。

### 7.3 一致性和展示

- 每篇笔记保存非负权威浏览总数；
- 每个笔记与去重主体组合只保存最后有效浏览时间，不保存完整浏览事件流水；
- 去重判断、最后浏览时间更新和总数增加在同一 PostgreSQL 事务或等价原子语义内完成；
- 并发上报不得突破 `30` 分钟去重窗口；
- 既有笔记迁移后浏览量为 `0`，不伪造历史数据；
- 首页频道卡片、个人主页笔记卡片和笔记详情展示浏览量；
- 视觉文案可对较大数量使用“万”等紧凑表示，无障碍名称必须暴露服务端返回的精确非负整数。

## 8. 回复与评论点赞通知

### 8.1 通知类型

- `COMMENT_REPLIED`：他人成功回复当前用户的评论或回复，默认文案为“回复了你的评论”；
- `COMMENT_LIKED`：他人首次把当前用户的评论或回复设置为已点赞，默认文案为“赞了你的评论”。

### 8.2 接收者和事务

- 回复直接目标的作者收到 `COMMENT_REPLIED`；
- 如果笔记作者既不是回复者也不是直接接收者，同时收到一条 `NOTE_COMMENTED`；
- 被点赞评论的作者收到 `COMMENT_LIKED`；
- 用户自己的操作不产生自己的通知；
- 回复或点赞关系写入与通知建立使用同一 PostgreSQL 事务；
- 重复幂等点赞不重复生成通知；
- 取消点赞不删除历史通知，取消后重新点赞可生成新通知；
- 不回填本 Spec 启用前的历史通知。

### 8.3 通知页行为

- `COMMENT_REPLIED` 归入“评论” Tab；
- `COMMENT_LIKED` 归入“赞和收藏” Tab；
- 点击后先标记已读，再进入对应笔记详情并定位、短暂高亮目标评论；
- 目标已删除时保留通知，进入原笔记并提示“相关评论已删除”；
- 笔记已不存在时沿用 SPEC-009 的安全降级规则。

## 9. 一对一私信

### 9.1 会话建立和唯一性

- 一个会话恰好包含两个不同用户；
- 同一用户对在系统中最多存在一个会话；
- 会话只在第一条消息成功持久化时建立，不产生空会话；
- 并发发送首条消息不得创建重复会话；
- 会话列表按最后消息时间倒序，无消息会话不存在；
- 他人公开主页显示“私信”按钮；未互相关注时按钮不可发送并说明“互相关注后可私信”；
- 当前用户自己的主页不显示私信按钮。

### 9.2 消息内容和发送

- 消息去除首尾空白后为 `1～1000` 个 Unicode 字符；
- 允许普通 Unicode 表情，不解析 HTML 或 Markdown；
- 每次发送都带有客户端生成的不透明请求 ID；
- 同一发送者的同一请求 ID 最多创建一条消息；
- 消息以服务端生成时间和 ID 确定稳定顺序；
- HTTP 发送为权威写入通道，数据库提交后再通过 WebSocket 向参与者推送；
- 推送失败不回滚已成功持久化的消息，客户端通过同步接口恢复；
- 发送失败时保留草稿，不在用户无感知时自动创建第二条消息。

### 9.3 历史、排序和同步

- 会话列表展示对方最新头像、昵称、最后一条消息预览、时间和未读数；
- 历史消息首次和每次向上加载 `30` 条；
- 接口使用稳定游标，传输可按新到旧分页，界面必须按旧到新展示；
- 加载更早消息时保持当前阅读位置，不突然跳到底部；
- WebSocket 重连、页面重新获得焦点或从后台恢复时，使用服务端游标同步遗漏消息；
- 客户端按消息 ID 去重，WebSocket 推送和 HTTP 响应不得显示两次。

### 9.4 已读和未读

- 会话对每个参与者保存服务端权威的最后已读边界；
- 打开会话、消息成功展示且页面处于可见状态时，把当前已展示的最新对方消息标记为已读；
- 后台页面、未打开会话或加载失败不自动标记已读；
- 左侧“私信”入口展示当前用户所有会话的消息未读总数；
- 会话列表展示每个会话未读数；
- 发送者只在自己最新一条已发送消息下显示“已读”或“未读”；
- 已读边界只能前进，重复请求或乱序 WebSocket 事件不得把已读状态倒退。

### 9.5 WebSocket 连接

- WebSocket 使用现有服务端会话 Cookie 认证，不在 URL 中传递 Cookie、会话 ID 或额外长期 Token；
- 握手时校验会话、Origin 和权限；
- 连接与用户绑定，不允许客户端指定其他用户作为接收者；
- 新消息和已读更新可以通过 WebSocket 实时到达；
- 连接断开不影响 HTTP 读写，界面显示可理解的“正在重连”状态而不清空历史或草稿；
- 当前基线只保证单服务器实例内的实时推送，持久化消息在任何情况下都可重新同步。

## 10. 数据模型与迁移

### 10.1 评论扩展

`NoteComment` 或等价模型至少支持：

- 所属笔记和作者；
- 根一级评论标识；
- 直接回复目标和目标作者；
- 删除时间或等价结构性占位状态；
- 按根评论和创建时间加载回复的索引；
- 循环、跨笔记和跨根回复不能通过服务端校验。

### 10.2 评论点赞

- 用户外键；
- 评论外键；
- 创建时间；
- 用户与评论组合唯一约束；
- 按评论统计和按用户查询的索引；
- 评论真实删除或转为占位时可原子清除点赞。

### 10.3 浏览量

- 笔记权威非负浏览总数；
- 笔记、主体类型、主体不可逆标识和最后有效浏览时间；
- 笔记与去重主体组合唯一约束；
- 支持原子去重与更新的索引。

### 10.4 会话和消息

- 会话唯一标识和两个参与者；
- 参与者对采用稳定规则归一化并唯一；
- 每个参与者的最后已读边界；
- 最后消息时间或等价高效列表排序能力；
- 消息唯一标识、会话、发送者、纯文本内容、客户端请求 ID 和服务端创建时间；
- 发送者与客户端请求 ID 组合唯一约束；
- 按会话、时间和 ID 分页的复合索引；
- 用户或会话未来如需删除，必须在新 Spec 中先定义私信保留和隐私语义。

### 10.5 迁移规则

- 空数据库可以安全执行全部迁移；
- 含既有用户、笔记、评论、互动、通知和资料的数据库可以无损升级；
- 既有评论全部视为一级评论；
- 既有评论点赞、回复、浏览量和私信初始为空；
- 不回填伪造数据；
- 所有唯一约束、外键和关键索引必须由数据库实际承载。

## 11. API 与实时契约

实际路径可按 NestJS 模块约定微调，但必须提供以下等价语义。

### 11.1 回复和点赞

- `GET /notes/:noteId/comments`：继续返回一级评论页，扩展回复预览、回复总数、点赞数和当前用户状态；
- `GET /notes/:noteId/comments/:rootCommentId/replies`：公开分页读取同一根下的回复；
- `POST /notes/:noteId/comments/:targetCommentId/replies`：登录用户发布回复；
- `PUT /comments/:commentId/like`：把目标设置为已点赞；
- `DELETE /comments/:commentId/like`：把目标设置为未点赞；
- 现有评论删除接口扩展占位语义；
- 写接口使用服务端会话确定操作者，不接受客户端传入作者 ID。

### 11.2 浏览上报

- `POST /notes/:noteId/views`：在详情展示后上报一次候选浏览；
- 响应至少返回是否计数和服务端权威浏览总数；
- 笔记不存在返回 `404`；
- 作者自访问或去重窗口内重复上报返回成功的未计数结果，不作为业务错误；
- 公开笔记列表和详情 DTO 返回权威浏览数。

### 11.3 私信 HTTP

- `GET /messages/conversations`：返回当前用户会话列表和稳定游标；
- `GET /messages/conversations/:conversationId`：返回会话元数据和当前发送权限；
- `GET /messages/conversations/:conversationId/messages`：返回历史消息和稳定游标；
- `POST /messages/users/:userId`：向指定互关用户发送首条或后续消息，必要时在同一事务创建会话；
- `POST /messages/conversations/:conversationId/messages`：在已知会话中发送消息；
- `PUT /messages/conversations/:conversationId/read`：把已读边界幂等推进到客户端已展示的服务端消息 ID；
- `GET /messages/unread-count`：返回当前用户私信未读总数；
- 所有私信接口要求有效登录，越权读取不得泄露会话是否存在。

### 11.4 WebSocket 事件

- 必须有可版本化的连接路径或事件契约；
- 服务端至少推送新消息、会话摘要更新、未读数更新和已读边界更新；
- 事件必须包含稳定 ID 或边界，使客户端可去重和拒绝倒退；
- 不向非会话参与者广播消息内容或未读状态；
- WebSocket 断开不得让持久化业务返回失败。

### 11.5 错误语义

- 未登录写操作和私信访问：`401`；
- 无权删除评论或访问会话：稳定的 `403` 或不泄露资源的 `404`；
- 笔记、评论、会话或目标用户不存在：`404`；
- 点赞自己评论、回复删除目标、用户给自己发私信或非互关状态发送：稳定 `4xx` 业务错误；
- 内容为空或超长：稳定字段校验错误；
- 服务端不返回 SQL、堆栈、Cookie、哈希标识或内部存储信息。

## 12. Web 交互和视觉结构

### 12.1 评论区

- 沿用小蓝书蓝色视觉体系和现有笔记详情右侧布局；
- 一级评论下缩进展示回复预览和“展开 N 条回复”；
- 每条有效评论或回复展示头像、昵称、作者标识、正文、时间、回复、点赞和有权限时的删除入口；
- 点赞选中状态不能只依赖颜色；
- 通知定位目标时在必要的分页中定位并短暂高亮，不因目标在后续页而默默失败；
- 回复增长由详情右侧内容区承担滚动，不制造 HTML 根元素假滚动或双重滚动。

### 12.2 私信页

- 共享左侧菜单增加“私信”入口和未读徽标；
- `/messages` 主内容使用会话列表与聊天区的双栏结构；
- 会话列表有稳定骨架、空状态、错误、重试、加载更多和选中状态；
- 聊天区显示对方资料、连接状态、历史、加载更早、草稿、字数、发送状态和发送权限；
- 会话没有新未读且用户未主动离开底部时，新消息后保持最新消息可见；
- 用户正在阅读更早消息时，新消息不强制拉回底部，显示“有新消息”快捷入口；
- 不满足互关条件时历史仍可读，输入区禁用并说明恢复条件；
- 新私信不写入 `/notifications` 通知列表，只更新私信会话和左侧未读徽标。

## 13. 安全、隐私与数据保留

- 所有写操作从服务端会话确定操作者；
- 回复归属、评论点赞对象、会话参与者和互关条件必须在服务端校验；
- 评论和私信按纯文本安全展示，防止 HTML 或脚本注入；
- 私信 API 和 WebSocket 不向第三方返回消息、已读边界、草稿或会话存在性；
- 会话列表和消息只返回必要公开资料，不返回邮箱、生日、对象 Key 或内部路径；
- 日志不记录评论正文、私信正文、访客 Cookie、去重哈希或认证凭据；
- 私信在本期永久保留，用户不能删除会话或消息；
- 未来增加用户注销、删除、撤回、拉黑、举报或保留期限时，必须新建 Spec 重新确认隐私与审计语义；
- 本期不承诺内容审核、反垃圾、用户拉黑或频率管理能力，互相关注是私信的业务访问门槛。

## 14. 一致性、并发与性能

- PostgreSQL 是回复、评论点赞、浏览量、私信和已读状态的唯一真实来源；
- 不使用 Redis 作为读缓存、计数器、未读缓存或 WebSocket 跨实例总线；
- 评论点赞、会话和消息幂等依赖数据库唯一约束，不只依赖前端防重；
- 评论/回复列表、通知列表、会话列表和消息历史不得产生随数量无界增长的 N+1 查询；
- 分页使用服务端稳定游标，并发新数据不得造成已加载数据大量重复或漏读；
- 浏览量不得为负数，并发去重请求最多增加一次；
- 消息先持久化再推送，任何 WebSocket 故障不得造成已确认消息丢失；
- 未读总数、会话未读数和已读边界在页面刷新后从服务端恢复；
- 私信模块必须为未来多实例广播预留替换边界，但本期不实现 Redis 适配器。

## 15. 状态与错误处理

- 评论预览、展开回复、点赞、定位和私信均有加载、空、失败和重试状态；
- 加载更多失败时保留已加载数据和游标位置；
- 删除、点赞、回复、发送和已读更新必须以服务端确认为准；
- 网络恢复后的重试不得创建重复点赞、会话、消息或浏览计数；
- 私信连接中断时保留已加载历史和未发草稿；
- 对方在发送前取消互关、会话被其他窗口读取、目标评论被删除等并发情况都安全收敛到服务端状态；
- 错误提示使用可理解的中文，不暴露技术细节。

## 16. 可访问性与自适应

- 回复、点赞、删除、加载更多、会话选择、发送和新消息入口可通过键盘完成；
- 按钮暴露可理解名称、选中/按下状态、数量和忙碌状态；
- 回复目标、长度提示、字段错误和发送状态可被辅助技术感知；
- 删除确认支持 Escape、焦点限制和合理焦点恢复；
- 新消息和已读更新使用不打断当前输入的可感知方式，不机械把每条消息作为紧急播报；
- 最低支持范围继续为宽度 `960 CSS px`、高度 `600 CSS px`；
- 在支持范围内，评论或私信空状态不制造 HTML 根元素假滚动；
- 评论由详情右侧内容区滚动，私信历史由聊天区滚动，不产生意外双重滚动；
- 低于最低宽度时，私信双栏退化为会话列表与聊天页之间切换，所有关键操作仍可达。

## 19. 验收标准

### AC-001：数据模型与迁移

- 空库和含既有业务数据的历史库均可安全迁移；
- 评论层级/删除状态、评论点赞、浏览去重、会话、消息和已读边界具备正确约束与索引；
- 既有数据不变，新统计和关系不伪造回填。

### AC-002：两级回复

- 可以回复一级评论和回复；
- 回复其他回复时扁平归属正确根评论并显示直接目标；
- 跨笔记、跨根、循环或已删除目标被拒绝；
- 内容长度、纯文本和登录草稿规则正确。

### AC-003：回复排序、分页和计数

- 一级评论倒序、回复正序和相同时间的 ID 边界稳定；
- 默认 `3` 条预览、每次 `10` 条展开和加载失败保留正确；
- 评论总数包含有效一级评论和回复，不包含删除占位。

### AC-004：删除与占位

- 作者和笔记作者权限正确，无权用户被拒绝；
- 无引用目标真实删除，仍承载或被引用的目标安全转为占位；
- 占位不泄露原文，下属回复保留，点赞清除，总数正确更新。

### AC-005：评论点赞

- 有效一级评论和回复可点赞/取消；
- 自己的内容不可点赞；
- 唯一约束、幂等、并发、真实计数和界面回滚正确；
- 未登录可读且操作进入登录意图恢复。

### AC-006：回复与点赞通知

- 直接被回复者、笔记作者和被点赞评论作者按去重规则收到正确通知；
- 业务写入和通知同事务成功或失败；
- 自己操作、重复幂等请求和取消点赞不产生错误通知；
- 通知分类、已读、定位高亮和目标删除降级正确。

### AC-007：有效浏览量

- 详情成功展示后可以增加浏览量；
- 卡片曝光、作者自访问和 `30` 分钟内重复访问不增加；
- 超过窗口后可再计数；
- 并发上报最多增加一次，页面刷新后恢复权威非负总数。

### AC-008：匿名浏览隐私

- 匿名访客可以通过随机 Cookie 去重；
- 数据库和日志不包含原始 Cookie、IP、User-Agent 或设备指纹；
- 访客标识不可从数据库直接还原；
- Cookie 或上报失败不阻断公开笔记浏览。

### AC-009：私信认证与会话权限

- 未登录按规则进入登录流程；
- 只有互相关注的不同用户可以发送；
- 同一用户对只有一个非空会话；
- 只有会话参与者可以读取，越权请求不泄露内容或资源存在性；
- 取消互关后历史可读但禁止新发送，恢复互关后恢复原会话。

### AC-010：消息持久化与幂等

- `1～1000` 字纯文本规则正确；
- 首条消息与会话在同一事务成功或失败；
- 相同发送者和客户端请求 ID 的网络重试只创建一条消息；
- 服务端排序、`30` 条分页、历史向上加载和滚动位置正确。

### AC-011：实时、断线与补偿

- 新消息持久化后在第二个独立上下文中实时出现；
- WebSocket 断开时 HTTP 仍可发送；
- 重连或窗口恢复后同步遗漏消息；
- HTTP 响应与 WebSocket 事件去重，不丢失也不重复显示；
- 无效会话、非同源连接和越权订阅被拒绝。

### AC-012：已读与未读

- 会话未读、私信入口总未读和页面刷新恢复正确；
- 只有在对应会话成功展示且页面可见时标记已读；
- 已读边界幂等前进且不倒退；
- 发送者最新一条消息的已读/未读状态与接收者边界一致。

### AC-013：Web 交互、自适应和可访问性

- 评论回复、点赞、删除、定位和私信主流程可通过键盘完成；
- `/messages` 双栏、空/错误/重试/禁止发送状态正确；
- `960×600` 及以上不出现根元素假滚动、关键内容裁切或意外双重滚动；
- 低于最低宽度时会话列表和聊天区可切换访问；
- 焦点、状态、数量和错误可被辅助技术感知。

### AC-014：安全、隐私与错误

- 评论和私信不执行 HTML 或脚本；
- 公开评论、通知、私信和浏览响应不泄露邮箱、生日、Cookie、哈希、对象 Key、内部路径、SQL 或堆栈；
- WebSocket 会话、Origin 和用户绑定校验正确；
- 日志不记录评论/私信正文或访客识别秘密；
- 失败使用稳定中文错误并保留用户已加载内容和草稿。

### AC-015：兼容性与回归

- 既有登录、个人主页、发布、频道、笔记详情、笔记点赞/收藏/关注、搜索、通知和资料设置继续工作；
- 评论总数扩展不破坏旧评论列表；
- 新通知类型不破坏旧通知分页、未读和失效降级；
- 浏览量和私信不改变推荐、频道或搜索排序；
- 公开页面在过期/无效 Cookie 下仍可正常阅读。

## 20. 风险与后续复审

- 评论占位与扁平回复对删除、分页和通知定位有较高一致性风险；
- 浏览量是“`30` 分钟去重的有效访问”，不是严格独立用户统计；
- 匿名 Cookie 可被清除，无法提供反欺诈级精度；
- 实时私信增加长连接、重连、已读竞态和双上下文验证成本；
- 单实例 WebSocket 不能直接支持未来多实例广播，扩容前必须复审 Redis 适配器或其他消息总线；
- 本期不包含拉黑、举报和陌生人消息，任一能力纳入前必须重新确认安全边界；
- 未来增加消息删除、撤回或用户注销时，必须先定义双方历史、审计和隐私保留语义。
