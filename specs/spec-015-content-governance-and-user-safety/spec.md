## 1. 背景

小蓝书已经完成认证、内容发布、推荐与频道、搜索、互动、通知、私信、个人主页和作者笔记管理，但目前缺少用户自主保护与平台基础治理能力。用户无法举报违规笔记、评论或账号，无法拉黑骚扰者，也不能删除自己已经发布的评论；平台没有管理员审核入口，无法隐藏违规内容或暂停违规账号。

本 Spec 建立第一版完整但克制的治理闭环：用户举报、双向隔离式拉黑、本人评论软删除、管理员人工审核、内容隐藏与恢复、账号封禁与恢复，以及可追溯的审核日志。所有处置由管理员明确确认，本期不使用举报数量自动处罚。

## 2. 已确认目标

- 登录用户可以举报笔记、评论和用户；
- 举报使用固定原因并允许补充简短说明；
- 用户可以在【我的举报】查看处理状态，但看不到管理员身份或内部理由；
- 用户可以拉黑其他用户，拉黑后双方在内容、互动和私信层面互相隔离；
- 拉黑时移除双方现有关注关系，解除拉黑后不自动恢复；
- 用户可以在【更多 → 黑名单管理】查看并解除自己发起的拉黑；
- 用户可以删除自己的一级评论或回复，删除后保留回复树，但删除项本身不在界面展示；
- 管理员可以在独立后台审核举报、隐藏或恢复内容、封禁或恢复普通账号；
- 封禁账号立即失效全部会话，且在恢复前不能登录；
- 所有管理员处置必须填写理由并写入不可变审计日志；
- 举报不会按数量自动隐藏内容或封禁账号。

## 3. 范围

### 3.1 本期包含

- 笔记、评论和用户举报入口与举报对话框；
- 固定举报原因、补充说明、重复提交收敛与频率限制；
- 【我的举报】列表、分页和通用处理结果；
- 用户拉黑、双向有效隔离、关注关系清理和解除拉黑；
- 【更多 → 黑名单管理】页面；
- 自己评论与回复的软删除及界面隐藏；
- `USER`、`ADMIN` 角色和 `ACTIVE`、`SUSPENDED` 账号状态；
- `/admin/moderation` 管理员举报审核页；
- 举报驳回、笔记隐藏/恢复、评论隐藏/恢复、账号封禁/恢复；
- 管理员处置理由和不可变审计日志；
- 封禁会话失效、登录门禁和公开内容过滤；
- 数据库迁移、REST/OpenAPI、前后端测试和相关 Browser E2E；
- 推荐、频道、视频、搜索、主页、详情、互动、通知和私信的治理过滤回归。

### 3.2 本期不包含

- 私信举报、图片单独举报或文件指纹举报；
- 举报结果站内通知、封禁通知或处罚消息；
- 用户申诉、管理员复核、多人审核或工单流转；
- 举报数量触发的自动隐藏、自动封禁或机器审核；
- 定时封禁、处罚等级、警告、禁言或限流；
- 管理员永久删除笔记、评论或账号；
- 法律保留、证据导出、内容完整快照或外部合规系统；
- 复杂 RBAC、管理员团队、细粒度权限或后台角色管理 UI；
- Redis 业务缓存、消息队列或搜索引擎；
- Browser E2E 纳入常规手动 CI。

## 4. 角色、权限与可见性

### 4.1 未登录用户

- 可以继续浏览未隐藏、未封禁且符合既有公开规则的内容；
- 不显示可执行的举报、拉黑、删除评论或后台操作；
- 尝试直接调用写接口时返回认证错误；
- 被管理员隐藏的内容和被封禁账号的资料对其表现为不存在。

### 4.2 普通登录用户

- 可以举报他人的笔记、评论和账号；
- 不能举报自己、自己的笔记或自己的评论；
- 可以拉黑其他普通用户，但不能拉黑自己；
- 只能管理自己主动建立的黑名单记录；
- 只能删除自己的评论或回复；笔记作者不能因此删除他人的评论；
- 不能访问管理员页面或管理员接口。

### 4.3 管理员

- 管理员在普通用户能力之外，可以访问 `/admin/moderation` 和对应接口；
- 管理员可以查看举报者身份、被举报目标和审核上下文；
- 管理员的每次处置必须填写理由；
- 本期后台只允许封禁或恢复 `USER` 账号，不允许管理员通过后台封禁自己或其他 `ADMIN`；
- 管理员角色只能通过仓库提供的本地 CLI 命令授予或撤销，不提供网页入口。

### 4.4 服务端权威边界

- 当前用户、角色和账号状态始终从服务端会话与数据库确定；
- 所有权限、目标归属、拉黑关系、内容状态和频率限制都必须由服务端校验；
- 前端隐藏按钮不能代替服务端权限控制；
- 非管理员访问后台页面或接口统一表现为 `404`，不暴露后台是否存在；
- 被拉黑、隐藏、封禁或不存在的目标按不泄露状态的响应规则处理。

## 5. 举报目标与入口

### 5.1 支持目标

- 笔记：图文和视频笔记；
- 评论：一级评论和回复；
- 用户：公开用户账号；
- 本期不接受私信或会话举报。

### 5.2 入口

- 笔记详情的“更多操作”提供【举报笔记】；
- 评论与回复的“更多操作”提供【举报评论】；
- 他人公开主页的“更多操作”提供【举报用户】与【拉黑用户】；
- 作者自己的内容和当前用户自己的主页不显示对应自举报入口；
- 入口必须有明确的可访问名称，打开对话框不能触发卡片跳转或其他互动。

## 6. 举报提交规则

### 6.1 固定原因

举报人必须选择以下一个原因：

- 色情低俗；
- 暴力血腥；
- 仇恨攻击；
- 骚扰；
- 人身攻击；
- 垃圾广告；
- 侵权；
- 其他。

可以额外填写 `0～200` 个用户可见字符的补充说明。说明为纯文本，去除首尾空白，不解析 HTML 或 Markdown。

### 6.2 创建、幂等与频率

- 只有登录且状态正常的用户可以提交；
- 不能举报自己，以及自己创作的笔记、评论或回复；
- 服务端创建前必须确认目标当前存在且对举报人可访问；
- 同一举报人针对同一目标同时只能存在一条 `PENDING` 举报；
- 重复提交同一待处理目标时返回已有举报，不创建第二条；
- 旧举报已经结束后可以重新举报同一目标，但仍受频率限制；
- 每个用户在任意连续 `60` 分钟内最多成功创建 `10` 条新举报；幂等返回已有记录不占用新额度；
- 达到上限时返回稳定错误和可理解提示，不丢失对话框内输入。

### 6.3 举报状态

- `PENDING`：等待管理员处理；
- `ACTIONED`：管理员已对目标采取处置；
- `DISMISSED`：管理员判断无需处置；
- `TARGET_UNAVAILABLE`：目标在处理前已由作者删除或已经不可用。

举报状态结束后不可回到 `PENDING`。管理员对某个目标执行隐藏或封禁处置时，同一目标的全部待处理举报在同一事务中进入 `ACTIONED`；单独驳回一条举报不会自动驳回同目标的其他待处理举报。

## 7. 我的举报

- 在【更多】菜单中增加【我的举报】，进入 `/settings/reports`；
- 列表只返回当前用户自己创建的举报；
- 每页 `20` 条，使用稳定游标，按 `createdAt DESC, id DESC` 排序；
- 展示目标类型、举报原因、提交时间和通用结果；
- 待处理显示“处理中”；
- 已处置显示“已采取措施”；
- 已驳回显示“未发现违规”；
- 目标不可用显示“目标已失效”；
- 举报人不能看到管理员账号、管理员内部理由、其他举报人或同目标举报数量；
- 本期不发送举报状态变化通知，用户通过该页面主动查看结果；
- 目标已不可访问时不回填完整标题、正文、评论或用户资料，不显示已删除内容快照。

## 8. 拉黑模型

### 8.1 建立拉黑

- 用户从他人公开主页的“更多操作”选择【拉黑用户】；
- 操作前显示确认对话框，说明双方将无法互相查看内容或互动；
- 拉黑关系以发起者和目标用户的方向性记录保存；
- 只要任意方向存在有效拉黑记录，双方之间都按互相隔离处理；
- 已经处于有效隔离时重复拉黑必须幂等收敛；
- 拉黑自己、拉黑不存在或不可操作账号必须被服务端拒绝。

### 8.2 原子关系清理

- 建立拉黑与删除双方现有关注关系必须在同一数据库事务完成；
- 同时删除“当前用户关注对方”和“对方关注当前用户”两个方向；
- 不删除双方历史点赞、收藏、评论、消息和业务审计记录；
- 不产生自动关注、取消关注或拉黑通知。

### 8.3 双向隔离范围

有效拉黑期间，双方均不能：

- 查看对方公开主页、笔记详情、推荐/频道/视频/搜索中的对方内容；
- 在个人主页的笔记、收藏、点赞等列表看到对方内容；
- 查看对方发表的评论或回复；
- 关注对方，或对对方笔记执行点赞、收藏、评论与回复；
- 对对方评论点赞或回复；
- 向对方发送新私信。

双方既有点赞、收藏和评论不从数据库删除。它们只在双方彼此查看时隐藏；未参与拉黑的其他用户仍可按原规则看到这些公开互动。

### 8.4 私信与通知

- 双方历史私信会话和消息继续保留并可只读查看；
- 输入区明确禁用，所有 HTTP 与 WebSocket 发送通道都必须拒绝新消息；
- 拉黑发生前双方产生的历史通知从双方通知列表中永久隐藏，但保留数据库记录；
- 拉黑期间不再创建双方之间的新互动通知；
- 解除拉黑后，已隐藏的历史通知不重新出现。

## 9. 黑名单管理与解除拉黑

- 在【更多】菜单增加【黑名单管理】，进入 `/settings/blocked-users`；
- 页面只列出当前用户主动拉黑的用户，不泄露哪些用户拉黑了当前用户；
- 每页 `20` 人，按最近拉黑优先稳定分页；
- 用户行展示仍允许公开的最小身份信息和【解除拉黑】按钮；
- 解除拉黑前必须确认，操作幂等；
- 解除拉黑只删除当前用户发起的方向记录；若对方仍有独立拉黑记录，双向隔离继续有效且不泄露原因；
- 解除后不恢复任何方向的关注关系；
- 双方必须重新互相关注，才可以按 SPEC-011 恢复发送私信；
- 解除拉黑不会重新展示拉黑前已隐藏的通知；
- 页面具备骨架、空状态、失败、重试和分页加载状态。

## 10. 删除自己的评论或回复

- 一级评论与回复作者均可删除自己的内容；
- 笔记作者不能仅凭笔记归属删除其他用户的评论；
- 删除前显示确认对话框，取消、关闭或 Escape 不改变数据；
- 删除使用软删除保留数据关系，不级联删除已有回复；
- 用户主动删除的评论或回复在公开评论区不显示【该评论已删除】或其他占位；
- 如删除的一级评论仍有有效回复，回复继续展示，不展示被删除项的原作者、头像、正文、发布时间、地区、点赞数或操作按钮；
- 该评论的回复继续保留原有层级和顺序；
- 已删除评论不能继续点赞、回复、举报或再次编辑；
- 重复删除幂等收敛，不产生重复通知或破坏回复树；
- 删除前已经产生的通知遵守既有数据保留规则，但通知预览不得继续泄露被删除正文。

## 11. 管理员角色与 CLI

- 用户角色至少包含 `USER` 和 `ADMIN`，历史用户迁移后默认是 `USER`；
- 账号状态至少包含 `ACTIVE` 和 `SUSPENDED`，历史用户默认是 `ACTIVE`；
- 仓库提供本地 CLI，通过运行时输入的邮箱授予或撤销 `ADMIN`；
- 管理员邮箱不得写入 Git 跟踪的 `.env`、JSON、TypeScript 配置、测试夹具或文档；
- CLI 必须验证目标用户存在、输入角色合法，并输出不含凭据的明确结果；
- 角色变更必须使既有授权状态失效，后续请求重新以数据库角色判断；
- 网页端本期不提供管理员角色授予、撤销或管理员列表功能。

## 12. 管理员审核页面

### 12.1 路由与访问

- 后台固定路由为 `/admin/moderation`；
- 非管理员访问页面、RSC 数据或 REST 接口统一返回 `404`；
- 管理员页面不出现在普通用户导航中；
- 管理员会话失效、角色撤销或账号封禁时立即失去访问权限。

### 12.2 举报列表

- 每页固定 `20` 条，按 `createdAt DESC, id DESC` 稳定排序；
- 可以按举报状态和目标类型筛选；
- 展示举报者、原因、补充说明、时间、目标状态和必要上下文；
- 不执行逐行 N+1 查询；
- 目标仍存在时提供受控预览或安全跳转；目标已失效时只显示类型、目标 ID、时间和审计信息；
- 加载、空、失败、筛选和分页状态明确且可恢复。

## 13. 管理员处置

### 13.1 可执行动作

- 驳回举报；
- 隐藏笔记；
- 恢复笔记；
- 隐藏评论或回复；
- 恢复评论或回复；
- 封禁普通用户账号；
- 恢复普通用户账号。

本期不允许管理员永久删除任何笔记、评论或账号。

### 13.2 通用处置规则

- 每次处置必须填写去除首尾空白后的非空理由，最长 `500` 个用户可见字符；
- 处置理由为管理员内部信息，不向举报人或被举报人展示；
- 管理员必须经过确认才能执行隐藏、恢复、封禁或恢复账号；
- 重复执行已经达到的目标状态必须幂等返回，不产生重复审计副作用；
- 处置、相关举报状态变化和审计记录必须在同一数据库事务中提交；
- 对目标执行实际处置时，同目标全部 `PENDING` 举报转为 `ACTIONED`；
- 驳回仅结束当前举报并转为 `DISMISSED`；
- 本期不向举报人或目标用户发送新的站内通知。

### 13.3 内容隐藏与恢复

- 隐藏不删除正文、媒体、互动或回复关系，允许管理员恢复；
- 普通用户访问隐藏笔记或隐藏评论时表现为不存在；
- 隐藏笔记作者可在自己的笔记列表或原详情看到只读占位【内容已被管理员隐藏】；
- 隐藏评论作者在原线程仍可访问时看到只读占位【内容已被管理员隐藏】；
- 作者不能编辑、删除、点赞、收藏、评论或以其他方式操作被隐藏内容；
- 管理员可在审核上下文中查看被隐藏内容；
- 恢复后内容以原创建时间、原排序和原互动数据重新可见，不作为新内容顶到列表顶部。

### 13.4 账号封禁与恢复

- 封禁为无限期状态，直到管理员明确恢复；
- 封禁成功后必须立即使该用户全部现有会话失效；
- 被封禁用户不能登录、刷新会话、发送 WebSocket 消息或执行任何认证写操作；
- 普通用户看不到该账号的公开主页、笔记、评论和回复；
- 既有内容、互动、关注、私信和审计数据不永久删除；
- 对方的历史私信可保留为只读记录，但不能向被封禁账号发送新消息；
- 恢复后账号和未被单独隐藏的内容按原数据重新可见，不恢复封禁期间未发生的互动；
- 本期不设置自动到期时间，也不提供被封禁用户申诉入口。

## 14. 目标删除与状态收敛

- 作者永久删除被举报笔记时，不为治理系统额外保存标题、正文或媒体快照；
- 用户删除被举报评论时，不为举报页保留可展示的原评论正文；
- 目标删除后，针对该目标的全部 `PENDING` 举报进入 `TARGET_UNAVAILABLE`；
- 举报记录保留举报人、目标类型、目标 ID、原因、说明、创建时间和状态审计；
- 【我的举报】与管理员页仅显示目标已失效，不回填内容；
- 目标已失效后不能执行隐藏、恢复或封禁目标内容等不适用处置；
- 用户账号不提供自助删除，因此用户举报的目标失效只处理未来可能出现的账号删除兼容场景。

## 15. 审计日志

- 每次管理员处置写入独立、追加式审计记录；
- 记录至少包含管理员 ID、动作、目标类型、目标 ID、内部理由、处置前状态、处置后状态和发生时间；
- 审计记录创建后不能通过业务 API 编辑或删除；
- 恢复是新的审计动作，不覆盖原隐藏或封禁记录；
- 普通用户、举报人和被举报人均不能访问审计日志；
- 日志与错误输出不得记录邮箱验证码、会话 Cookie、SMTP 授权码、私信正文或完整内容正文；
- 管理员身份和内部理由只在管理员授权页面与受控数据库中可见。

## 16. 数据模型与一致性

- PostgreSQL 是举报、拉黑、评论删除状态、角色、账号状态、内容治理状态和审计日志的唯一真实来源；
- 本期不使用 Redis 缓存上述业务状态；
- 拉黑记录对“发起者 + 目标用户”建立唯一约束；
- 待处理举报使用事务或兼容唯一约束保证同一举报人/目标最多一条；
- 举报、黑名单和后台列表使用与排序一致的索引和稳定游标；
- 内容隐藏状态与作者删除状态必须可区分；
- 评论软删除不能破坏父子外键和回复排序；
- 拉黑及双向取消关注必须原子完成；
- 管理员处置、举报状态批量更新和审计写入必须原子完成；
- 封禁与会话失效必须具备服务端权威机制，不能依赖客户端清除 Cookie；
- 既有历史数据迁移不得改变公开内容、关注、互动、私信或通知语义。

## 17. 查询过滤与防绕过

- 推荐、频道、视频页、搜索、个人主页、详情和相关计数必须排除管理员隐藏及封禁账号内容；
- 登录用户的所有内容与评论查询还必须应用有效拉黑关系；
- 互动写接口在事务前重新检查拉黑、封禁、隐藏和删除状态；
- 通知列表过滤拉黑时已经持久标记隐藏的通知，不在解除拉黑后重新展示；
- 私信 HTTP 写入和 WebSocket 推送都检查互关、拉黑和账号状态；
- 不能通过猜测 ID、分页游标、通知预览、收藏列表、点赞列表或历史缓存绕过过滤；
- 聚合计数不得因为过滤而泄露对方身份或后台处置状态；
- 公开接口不返回举报数量、举报者身份、内部审核理由或管理员身份。

## 18. 状态与错误响应

- `400/422`：原因、说明、处置理由或目标类型不合法；
- `401`：未登录、会话失效或被封禁账号尝试认证操作；
- `404`：目标不存在、被隐藏、被封禁、被拉黑隔离、非管理员访问后台，或按安全策略不应泄露的资源；
- `409`：不兼容的当前状态或无法执行的治理动作；
- `429`：连续 60 分钟举报数量达到上限；
- 重复待处理举报返回已有记录，不作为错误；
- 失败响应使用稳定错误码和中文消息，不返回 SQL、堆栈、内部对象 Key、绝对路径、Cookie 或私有内容；
- 前端失败时保留可恢复输入，不使用演示数据伪装成功。

## 19. 页面、布局与可访问性

- 举报、拉黑、删除评论和管理员危险操作均使用可访问确认/表单对话框；
- 对话框打开时焦点进入，Tab 不逃逸，关闭后焦点返回触发按钮；
- Escape 只关闭未提交对话框，不执行危险动作；
- 忙碌时禁用重复提交，并通过文本或 `aria-live` 表达结果；
- 键盘可完成举报、拉黑、解除拉黑、删除评论和管理员审核主流程；
- `960×600` 为最低支持视口，页面使用自适应高度与明确的单一滚动容器；
- 列表加载、空、失败、重试和分页状态不制造根元素假滚动；
- 长昵称、长原因和 `200/500` 字符文本不挤压关键按钮；
- `prefers-reduced-motion` 下不依赖动画表达状态。

## 20. 性能与安全

- 后台、我的举报和黑名单每页 `20` 条，不一次加载全量数据；
- 列表关联用户与目标摘要必须批量查询，避免逐行 N+1；
- 拉黑过滤和封禁/隐藏过滤应由数据库查询或可证明等价的服务端批量策略完成；
- 举报频率限制基于数据库权威记录，进程重启后仍生效；
- 所有写操作继续执行 Origin/CSRF、会话、条款版本和年龄门禁；
- 举报说明与管理员理由按纯文本处理并限制长度；
- 管理员接口不能仅依赖路由名称或前端组件保护；
- CLI 不接受写入仓库的管理员邮箱清单，不打印敏感配置；
- 不记录或返回已删除目标的完整内容快照。

## 21. 数据迁移与兼容性

- 历史用户回填 `USER` 与 `ACTIVE`；
- 历史笔记与评论默认处于未隐藏状态；
- 现有评论回复树、点赞关系、关注关系、通知和私信迁移后保持不变；
- 新评论删除字段必须允许历史评论无损升级；
- 新角色、状态和治理字段必须使用显式默认值并具备必要索引；
- 空库应用全部迁移和从 SPEC-014 历史库升级均须成功；
- OpenAPI、Prisma Schema、DTO 校验和实际错误码保持一致。

## 22. 测试与验收策略

- 实施阶段先运行举报、拉黑、评论删除、管理员权限、封禁会话和查询过滤的定向单元/集成测试；
- 初次实施完成运行受影响静态检查、单元/集成测试、生产构建和相关 Chromium Browser E2E；
- 初次独立验收逐项验证 AC-001 至 AC-018，并只运行一次完整 Browser E2E；
- Chromium 覆盖举报、拉黑、评论删除和管理员审核主流程；
- Firefox/WebKit 只覆盖对话框焦点、滚动、历史导航等确有浏览器差异风险的场景；
- 小范围返工只运行历史失败项和直接受影响回归，不机械重复完整 E2E；
- 同一最终工作区状态下已有可信完整 E2E 时，后续复验按项目规则复用该结果；
- 常规手动 CI 不安装浏览器、不运行 Browser E2E，CI 结果不作为 Spec 完成门禁；
- 测试账号、举报说明和审核理由不得包含真实隐私或凭据。

## 23. 验收标准

### AC-001：迁移与历史兼容

- 空库和 SPEC-014 历史库迁移成功；
- 历史用户、内容、评论、互动、关注、通知和私信无损；
- 角色、账号状态、举报、拉黑、治理状态和审计约束正确；
- OpenAPI 与真实接口和错误一致。

### AC-002：举报入口与字段

- 登录用户可从笔记、评论/回复和他人主页进入举报；
- 未登录和自举报被拒绝；
- 八个固定原因、可选 `0～200` 字说明和纯文本规则正确；
- 提交成功显示明确反馈且不泄露后台信息。

### AC-003：举报幂等与频率限制

- 同一用户、同一目标只存在一条待处理举报；
- 重复提交返回已有记录且不占新额度；
- 连续 60 分钟最多创建 10 条，进程重启后规则仍有效；
- 并发提交不能绕过唯一性或频率限制。

### AC-004：我的举报

- 只返回当前用户的举报；
- 每页 20 条、稳定排序和分页；
- 四类状态映射为确认的通用中文结果；
- 不显示管理员身份、内部理由、其他举报人、举报数量或失效内容快照。

### AC-005：建立拉黑与关注清理

- 拉黑需要确认且重复请求幂等；
- 任一方向拉黑后双向隔离立即生效；
- 两个方向的既有关注关系在同一事务删除；
- 拉黑失败不会出现只删关注或只建拉黑的中间状态。

### AC-006：拉黑内容与互动隔离

- 双方互相看不到主页、笔记和评论；
- 推荐、频道、视频、搜索、详情、主页列表和历史缓存均不能绕过；
- 关注、点赞、收藏、评论、回复和评论点赞均被服务端拒绝；
- 旧互动不删除，第三方用户仍按原规则可见。

### AC-007：拉黑私信与通知

- 历史私信可读但所有发送通道禁用；
- 拉黑期间不产生双方新互动通知；
- 既有双方通知被持久隐藏；
- 解除拉黑后旧通知不重新出现，且必须重新互关才能发送私信。

### AC-008：黑名单管理与解除

- 【更多 → 黑名单管理】只列出当前用户主动拉黑的人；
- 每页 20 人、最近拉黑优先稳定分页；
- 解除需要确认、幂等且不恢复关注；
- 对方仍有反向拉黑时隔离继续生效且不泄露该事实。

### AC-009：删除自己的评论

- 用户只能删除自己的评论或回复，笔记作者不能删除他人评论；
- 删除后原位置直接消失，不显示【该评论已删除】、身份、正文、时间、点赞或操作；存在有效回复时仅保留回复内容；
- 回复树、层级和顺序保持；
- 重复删除安全收敛，已删除评论不能继续互动或举报。

### AC-010：管理员访问与角色 CLI

- 只有 `ADMIN` 可以访问 `/admin/moderation` 和接口；
- 普通用户和匿名访问统一为 404；
- CLI 可按运行时邮箱授予和撤销角色，仓库不保存管理员邮箱；
- 角色撤销后既有后台授权立即失效。

### AC-011：管理员举报列表

- 每页 20 条、最新优先，支持状态和目标类型筛选；
- 管理员可见举报者和必要上下文；
- 目标失效时只显示最小审计信息；
- 加载、空、失败、筛选、分页和 N+1 控制正确。

### AC-012：举报驳回和批量状态收敛

- 驳回必须填写内部理由，只结束当前举报；
- 对目标执行处置时，同目标全部待处理举报原子转为 `ACTIONED`；
- 举报人只看到通用结果；
- 不产生举报或处罚通知。

### AC-013：内容隐藏与恢复

- 普通用户无法访问隐藏笔记或评论；
- 作者只能看到【内容已被管理员隐藏】只读占位，不能操作；
- 管理员仍可在审核上下文查看；
- 恢复后以原时间、排序、媒体和互动重新可见。

### AC-014：账号封禁与恢复

- 只可封禁普通账号，处置无限期且需要理由；
- 封禁后全部会话立即失效并拒绝重新登录；
- 主页、笔记、评论和回复对普通用户隐藏，私信不能发送；
- 恢复后未单独隐藏的数据重新可见。

### AC-015：目标删除与最小保留

- 被举报笔记或评论由作者删除后，待处理举报变为 `TARGET_UNAVAILABLE`；
- 不额外保留或展示完整内容快照；
- 类型、目标 ID、原因、时间和审计仍可查询；
- 不允许对失效目标执行不适用处置。

### AC-016：审计、事务与安全

- 每次管理员处置都有包含前后状态和理由的追加式审计；
- 审计不可通过业务 API 修改或删除；
- 拉黑、管理员处置和状态批量更新满足原子性；
- 权限、CSRF、输入长度、纯文本、错误脱敏和防 ID 绕过正确。

### AC-017：可访问性与自适应布局

- 举报、拉黑、删除和后台处置可通过键盘完成；
- 对话框焦点、关闭恢复、错误和忙碌状态可感知；
- `960×600` 下无关键裁切、根假滚动或不可达按钮；
- Chromium 主流程及 Firefox/WebKit 差异场景按分层策略通过。

### AC-018：完整回归与验证边界

- 登录、发布、推荐、频道、视频、搜索、主页、详情、互动、通知、资料、笔记管理和私信继续工作；
- 初次独立验收运行一次完整 Browser E2E；
- 同一最终状态不重复完整 E2E，小范围返工只复验失败项和受影响回归；
- 常规手动 CI 继续不运行 Browser E2E。

## 24. 风险与后续复审

- 双向隔离会影响大量读取和写入入口，必须建立共享服务端策略，避免只修前端；
- 通知在解除拉黑后仍不重新出现，需要持久抑制，而不能只做实时查询过滤；
- 账号封禁必须能使既有会话立即失效，不能等待 Cookie 自然过期；
- 管理员隐藏与作者永久删除是不同状态，恢复和目标失效不得混淆；
- 评论软删除保留回复树，接口保留结构语义，UI 隐藏用户主动删除项；
- 未来若增加私信举报、申诉、自动审核、定时处罚、管理员团队或永久管理删除，需要新的 Spec 和数据保留决策。
