## 1. 实施目标

- 建立用户举报、我的举报和管理员人工处理闭环；
- 建立服务端权威的双向隔离式拉黑和黑名单管理；
- 建立保留回复树的评论软删除；
- 建立角色、账号状态、内容隐藏状态和不可变审计；
- 使封禁能够立即撤销全部会话和登录能力；
- 将治理过滤一致应用到内容、互动、通知和私信入口；
- 在不重复完整 E2E 的前提下提供足够的独立验收证据。

### 前端

## 4. 数据与事务设计重点

- 拉黑记录保留方向性，但授权判断使用任一方向存在即隔离；
- 拉黑和双向关注删除必须使用一个事务；
- 历史通知需要在拉黑时持久抑制，不能仅用当前拉黑查询过滤；
- 解除当前用户方向的拉黑不能删除对方独立建立的记录；
- 举报频率限制与创建必须在并发下保持正确；
- 内容作者删除时，待处理举报状态收敛不能额外复制完整内容；
- 管理员处置、同目标举报批量状态和审计日志必须原子提交；
- 内容隐藏、作者删除和评论软删除使用可区分状态；
- 封禁会话失效必须覆盖所有设备、HTTP 和 WebSocket；
- 查询过滤应集中复用，不能在每个页面散落不同语义。

## 6. 风险与控制

| 风险 | 控制 |
| --- | --- |
| 只在前端隐藏导致 ID 绕过 | 共享服务端策略覆盖所有读写接口 |
| 拉黑成功但关注只删一边 | 拉黑和双向关系清理放入同一事务 |
| 解除拉黑后旧通知重新出现 | 拉黑时写入持久抑制状态 |
| 封禁后旧会话继续可用 | 用户级会话失效版本或索引覆盖全部会话 |
| 评论软删除破坏回复树 | 保留记录和父子外键，统一 tombstone 序列化 |
| 举报限流并发穿透 | 数据库权威计数与事务/锁保护 |
| 同目标举报状态不一致 | 管理员处置时事务批量更新 |
| 审计理由被覆盖 | 追加式审计，恢复写入新记录 |
| 隐藏与删除混淆 | 独立状态与独立响应语义 |
| 管理员误封管理员 | 后台只允许处置 `USER`，角色由 CLI 管理 |
