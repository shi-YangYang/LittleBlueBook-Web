## 1. 背景

SPEC-007 已经打通笔记点赞、收藏、评论和用户关注，但这些互动只改变业务数据，不会主动告知被互动用户。首页左侧已经存在“通知”入口，目前仍是“功能开发中”占位。

本 Spec 建立登录用户可访问的互动通知中心，使笔记作者能够看到他人对自己笔记产生的点赞、收藏和评论，使用户能够看到新增关注，并通过未读状态和目标跳转完成通知闭环。

## 2. 目标

- 左侧“通知”入口进入真实通知页面；
- 记录他人对当前用户产生的四类有效互动；
- 提供分类列表、稳定分页、加载、空、失败和重试状态；
- 提供单条已读、全部已读及全局未读数量；
- 从通知可靠进入笔记详情或互动用户公开主页；
- 复用现有邮箱登录弹框并恢复登录前的通知访问意图；
- 保持 PostgreSQL 单一真实来源，不引入实时基础设施；
- 遵守既有桌面自适应高度、滚动、隐私和可访问性约束。

## 3. 范围

### 3.1 包含

- 点赞笔记通知；
- 收藏笔记通知；
- 评论笔记通知；
- 新增关注通知；
- `/notifications` 通知页面；
- “全部”“评论”“赞和收藏”“新增关注”四个 Tab；
- 通知未读数量及左侧入口徽标；
- 单条通知标记已读；
- 一键将当前用户全部通知标记已读；
- 每页 `20` 条的稳定游标分页和加载更多；
- 笔记详情、用户公开主页目标跳转；
- 关联评论、笔记等目标已不存在时的安全降级；
- 认证、授权、迁移、OpenAPI、自动化测试和 Browser E2E。

### 3.2 不包含

- 私信或聊天；
- 系统公告、运营通知或审核通知；
- 评论回复、楼中楼、评论点赞或 `@` 提及；
- 邮件通知、浏览器系统通知、移动端推送或声音提醒；
- WebSocket、Server-Sent Events、轮询式实时推送或消息队列；
- Redis 通知缓存、未读计数缓存或事件流；
- 多人互动聚合为一条通知；
- 通知设置、免打扰或按类型关闭通知；
- 用户主动删除通知；
- 通知自动过期或后台清理；
- 推荐算法因通知行为改变；
- App 端。

## 4. 用户与权限

### 4.1 接收者

- 通知接收者是被互动对象的所有者：
  - 笔记点赞、收藏、评论的接收者为笔记作者；
  - 关注通知的接收者为被关注用户。
- 用户自己的动作不产生自己的通知，包括收藏或评论自己的笔记；
- 只有通知接收者本人可以读取通知、读取未读数量和修改已读状态；
- 其他登录用户、未登录用户和通知发起者均不得读取不属于自己的通知。

### 4.2 未登录访问

- 未登录点击左侧“通知”时，不跳转到独立登录页面；
- 打开现有邮箱登录弹框；
- 登录成功后自动进入 `/notifications`；
- 直接访问 `/notifications` 且没有有效会话时，同样进入登录流程；
- 登录失败、取消或关闭弹框时不得误进入通知页；
- 登录意图不得包含 Cookie、邮箱验证码或其他敏感信息。

## 5. 通知类型

| 类型 | 触发动作 | 接收者 | 默认文案 |
| --- | --- | --- | --- |
| `NOTE_LIKED` | 他人首次将目标笔记设置为已点赞 | 笔记作者 | `赞了你的笔记` |
| `NOTE_FAVORITED` | 他人首次将目标笔记设置为已收藏 | 笔记作者 | `收藏了你的笔记` |
| `NOTE_COMMENTED` | 他人在目标笔记成功发表一级评论 | 笔记作者 | `评论了你的笔记` |
| `USER_FOLLOWED` | 他人首次将目标用户设置为已关注 | 被关注用户 | `关注了你` |

- 每次有效互动生成一条独立通知；
- 本期不把多个用户或多次互动聚合为一条；
- 通知文案由受控类型映射生成，不允许客户端提交任意通知文案。

## 6. 生成与幂等规则

### 6.1 点赞、收藏和关注

- 只有业务状态从“未建立”变为“已建立”时生成通知；
- 已经处于目标状态时重复发送幂等 `PUT` 请求，不生成重复通知；
- 取消点赞、取消收藏或取消关注不生成通知，也不删除历史通知；
- 取消后再次建立关系属于新的有效互动，可以生成新的通知；
- 快速重复请求、网络重试和并发请求不得产生重复关系或同一次状态变化的重复通知；
- 点赞自己仍按 SPEC-007 被拒绝；
- 收藏自己的笔记和关注自己均不产生通知，其中关注自己仍按 SPEC-007 被拒绝。

### 6.2 评论

- 每条成功创建的他人一级评论生成一条通知；
- 笔记作者评论自己的笔记不生成通知；
- 评论创建失败时不生成通知；
- 客户端重试不得在服务端未创建新评论的情况下额外生成通知；
- 评论删除不删除历史通知。

### 6.3 事务边界

- 互动关系或评论写入与对应通知创建必须在同一个 PostgreSQL 事务中完成；
- 事务失败时互动与通知均不生效；
- 不允许出现互动已经提交但同步通知无故缺失，或通知存在但互动从未成功的中间状态；
- 通知创建不得通过 Redis、内存队列或未确认的异步任务代替本期事务保证。

## 7. 历史保留与目标失效

- 通知不提供主动删除；
- 通知不设置自动过期；
- 取消互动后历史通知仍然保留；
- 关联评论被删除时：
  - 通知继续存在；
  - 不再展示原评论正文；
  - 展示`相关评论已删除`；
  - 点击后标记已读，并在原笔记仍存在时进入笔记详情；
- 关联笔记不存在时：
  - 通知继续存在；
  - 缩略图使用不可用占位；
  - 点击后标记已读并提示`相关内容已不存在`；
  - 不跳转到错误或泄露内部信息的页面；
- 未来若支持用户注销，通知需安全显示`该用户已注销`或等价匿名状态，不得因关联用户缺失导致列表失败；
- 目标失效不应造成整个通知页加载失败。

## 8. 已读与未读

### 8.1 单条已读

- 新通知默认未读；
- 点击通知行时发起幂等已读更新；
- 已读通知再次点击不会重复增加或减少未读数量；
- 单条通知只能由接收者本人标记已读；
- 如果已读更新失败，前端最终以服务端状态为准，不得产生负数或永久错误徽标；
- 目标已失效的通知仍可被标记已读。

### 8.2 一键已读

- 通知页提供“一键已读”；
- 操作作用于当前用户的全部未读通知，不局限于当前 Tab、当前页或当前已加载数据；
- 接口必须幂等；
- 没有未读通知时按钮可禁用或安全返回成功；
- 操作成功后页面可见通知和左侧未读徽标同步更新；
- 操作失败时保留服务端真实未读状态并提供可理解的错误提示。

### 8.3 未读徽标

- 左侧“通知”入口在登录状态下获取当前用户未读数量；
- 未读数量为 `1～99` 时显示准确数字；
- 超过 `99` 时显示 `99+`；
- 未读数量为 `0` 时不显示红点或数字；
- 徽标不能只依赖颜色表达，必须包含可访问名称；
- 未登录状态不请求私有未读数量；
- 本期不承诺实时刷新：进入页面、刷新页面或重新导航时获取最新状态。

## 9. 列表、分类和分页

### 9.1 Tab

| Tab | URL 参数 | 包含类型 |
| --- | --- | --- |
| 全部 | `tab=all` 或省略 | 全部四类通知 |
| 评论 | `tab=comments` | `NOTE_COMMENTED` |
| 赞和收藏 | `tab=reactions` | `NOTE_LIKED`、`NOTE_FAVORITED` |
| 新增关注 | `tab=follows` | `USER_FOLLOWED` |

- 默认 Tab 为“全部”；
- 当前 Tab 写入 URL；
- 刷新、浏览器前进和后退恢复相同 Tab；
- 无效 Tab 安全回退到“全部”，不得请求任意未定义类型；
- 切换 Tab 不自动标记通知已读。

### 9.2 排序和分页

- 通知按 `createdAt DESC, id DESC` 稳定倒序；
- 每页固定 `20` 条；
- 使用不透明游标加载更多；
- 游标必须绑定当前用户和当前分类；
- 非法、篡改、跨用户或跨分类游标返回稳定 `400`；
- 分页不得重复或遗漏；
- 加载更多失败时保留已经加载的通知和当前游标位置；
- 没有下一页时不再显示可操作的加载更多按钮。

## 10. 通知行展示

每条通知至少展示：

- 发起者头像；
- 发起者当前公开昵称；
- 受控动作描述；
- 相对时间；
- 已读或未读的非纯颜色状态；
- 笔记相关通知的笔记缩略图或不可用占位；
- 评论通知最多两行的当前评论正文预览，评论已删除时显示删除状态。

展示规则：

- 笔记相关通知点击后进入对应笔记详情；
- 新增关注通知点击后进入发起者公开主页；
- 时间显示“刚刚、几分钟前、几小时前、几天前”等相对表达；
- 时间元素通过 `title`、`datetime` 或等价辅助信息提供服务端准确时间；
- 昵称、评论和内容字段按纯文本展示，不解析 HTML；
- 长昵称和评论不得挤压操作区域或制造横向根滚动；
- 通知行整体可点击，同时具备键盘和辅助技术可操作语义。

## 11. 页面设计

### 11.1 整体布局

- 路径为 `/notifications`；
- 视觉参考小红书网页版通知中心，但使用小蓝书现有蓝色品牌体系；
- 沿用当前页面外壳、左侧菜单和顶部搜索区域；
- 左侧“通知”在当前页面显示选中状态；
- 主区域依次展示页面标题、四个 Tab、“一键已读”和纵向通知列表；
- 不创建独立于现有设计系统的全新导航或卡片风格。

### 11.2 加载、空和失败

- 首次加载和切换 Tab 至少稳定展示约 `300ms` 骨架，避免骨架与空状态闪烁；
- 实际请求超过 `300ms` 时持续显示加载状态；
- 不允许通过固定延迟掩盖真实失败；
- 空状态文案：
  - 全部：`暂时没有通知`
  - 评论：`暂时没有评论通知`
  - 赞和收藏：`暂时没有赞和收藏通知`
  - 新增关注：`暂时没有新增关注`
- 首次加载失败显示明确错误和重试按钮；
- 重试时不得重复列表项；
- 单条目标不可用不得导致整页进入失败状态。

### 11.3 自适应高度和滚动

- 遵守 SPEC-005；
- 桌面最低支持范围为宽度 `960 CSS px`、高度 `600 CSS px`；
- 页面连续自适应，不枚举大量固定宽高组合；
- 空列表、少量通知或仅一行内容时不得出现 HTML 根元素假滚动；
- 内容超过视口时由正常页面主内容承担滚动；
- 不得出现根元素与内部列表双重滚动；
- Tab、“一键已读”和通知内容不得被固定高度裁切；
- 低于最低支持范围时内容仍需可访问。

## 12. 数据模型

通知持久化模型至少包含：

- 通知 ID；
- 通知类型；
- 接收者用户 ID；
- 发起者用户 ID，可为未来注销兼容预留空值；
- 关联笔记 ID，可空；
- 关联评论 ID，可空；
- 创建时间；
- 已读时间，可空。

约束和索引至少包括：

- 接收者外键；
- 发起者外键；
- 笔记和评论关联采用与历史保留规则一致的 `SET NULL` 或等价策略；
- 支持接收者按创建时间稳定分页的组合索引；
- 支持接收者按类型和创建时间分页的组合索引；
- 支持接收者未读数量查询的索引；
- `readAt IS NULL` 表示未读，非空表示已读；
- 不能依赖可修改昵称、文案或前端状态作为权限依据；
- 数据库迁移必须支持空库和已有互动数据的历史库；
- 不回填 SPEC-009 上线前已经存在的互动通知；
- 新通知只从 SPEC-009 正式启用后的有效互动开始产生。

## 13. API

建议接口：

### 13.1 通知列表

`GET /notifications`

查询参数：

- `tab`：`all | comments | reactions | follows`；
- `cursor`：可选不透明游标；
- `limit`：服务端限制最大值，本页面使用 `20`。

响应至少包含：

- 通知列表；
- 下一页游标；
- 每条通知的类型、已读状态、准确时间；
- 发起者公开信息；
- 可用目标和笔记缩略图；
- 评论当前预览或已删除状态。

### 13.2 未读数量

`GET /notifications/unread-count`

- 返回当前用户准确未读总数；
- 不按当前 Tab 限制；
- 必须登录。

### 13.3 单条已读

`PUT /notifications/:notificationId/read`

- 幂等地把当前用户的一条通知设置为已读；
- 返回最终已读状态和服务端确认的未读总数；
- 不属于当前用户时返回安全 `404`，避免泄露通知是否存在。

### 13.4 全部已读

`PUT /notifications/read-all`

- 幂等地标记当前用户全部通知已读；
- 返回最终未读总数 `0` 和本次更新数量；
- 不接受其他用户 ID。

### 13.5 通用接口要求

- 全部接口使用现有 Cookie 会话；
- 未登录返回统一 `401`；
- 参数错误返回稳定 `400`；
- 不存在或无权访问的通知返回安全 `404`；
- 响应遵循项目现有 API 包装和 OpenAPI 规范；
- 错误不得泄露 SQL、堆栈、内部对象 Key、邮箱或 Cookie。

## 14. 一致性、并发与性能

- PostgreSQL 是通知和未读状态的唯一真实来源；
- 本期不读取或写入 Redis 通知数据；
- 互动写入与通知创建共用数据库事务；
- 已读接口为幂等目标状态操作；
- 未读数量不得小于 `0`；
- 快速切换 Tab 时旧请求晚到不得覆盖当前 Tab；
- 快速连续点击通知或“一键已读”不得导致徽标回跳为错误值；
- 列表查询避免逐条无界 N+1；
- 所有分页和未读查询使用与过滤及排序匹配的索引；
- 本期不设未经生产数据支持的固定毫秒性能门槛，但代表性分页查询不得退化为无界全表扫描；
- 后续只有在生产指标证明 PostgreSQL 通知查询成为瓶颈时，才评估缓存、事件流或实时交付。

## 15. 安全与隐私

- 服务端从会话确定接收者，不接受客户端指定接收者；
- 发起者和目标对象从已提交的互动业务数据确定；
- 通知列表只返回发起者公开头像、昵称、小蓝书号等必要字段；
- 不返回发起者或接收者邮箱；
- 评论预览属于接收者原本可见的公开笔记评论，但接口仍只返回页面所需长度；
- 评论删除后不得继续返回被删除正文；
- 日志不记录评论完整正文、通知列表内容、Cookie、验证码或邮箱凭据；
- 通知 ID、游标和错误行为不能用于枚举其他用户通知；
- 纯文本输出需要防止 HTML 和脚本注入。

## 16. 可访问性

- Tab 使用正确的 Tab/TabPanel 或等价语义；
- 键盘可以操作 Tab、通知行、“一键已读”、重试和加载更多；
- 当前 Tab、未读、已读和加载状态不只依赖颜色；
- 未读徽标向辅助技术提供“通知，N 条未读”等可理解名称；
- 骨架不被辅助技术误读为真实通知；
- 异步成功和失败反馈具备合理的状态语义；
- 页面跳转后焦点位置合理，浏览器返回时不会丢失当前 Tab。

## 17. 测试与验收策略

### 17.1 实施阶段

- 数据迁移、外键、索引和历史库兼容测试；
- 四类通知生成、本人动作排除和事务回滚测试；
- 幂等请求、取消后重建、并发重复请求测试；
- 权限、未读、单条已读和全部已读测试；
- 分类、游标、非法游标和目标删除降级测试；
- 前端 Tab、URL、加载、空、失败、徽标和键盘测试；
- SPEC-007 互动闭环受影响回归；
- SPEC-009 Chromium Browser E2E；
- 静态检查、单元/集成测试、构建及数据库校验。

### 17.2 独立验收

- 验收 Agent 独立准备至少两个用户和代表性笔记；
- 首轮独立验收运行一次完整 Browser E2E；
- Chromium 重点覆盖完整通知业务闭环；
- Firefox 和 WebKit 聚焦 Tab、通知跳转、登录恢复、键盘和滚动差异；
- 验证 `960×600` 及连续尺寸变化下无裁切、假滚动和双重滚动；
- 不将 CI 作为 Spec 验收项；
- 后续小范围返工只复验历史失败项和受影响回归，除非触发扩大验证条件。

## 18. 验收标准

### AC-001：迁移与数据完整性

- 空库和已有数据历史库均可成功迁移；
- 通知类型、关系、外键和查询索引符合本 Spec；
- 关联评论或笔记删除不会错误删除整批历史通知；
- 不回填上线前历史互动。

### AC-002：四类通知生成

- 他人点赞、收藏、评论笔记以及关注用户分别产生正确通知；
- 自己操作自己的内容不产生通知；
- 通知接收者、发起者、类型和目标正确。

### AC-003：幂等、取消和事务

- 重复幂等请求不产生重复通知；
- 取消不产生或删除通知；
- 取消后重新建立关系可产生新通知；
- 互动与通知在同一事务中成功或失败。

### AC-004：认证与权限

- 未登录无法读取或修改通知；
- 登录用户只能访问自己的通知；
- 越权通知 ID 返回安全结果；
- 登录成功后恢复 `/notifications` 访问意图。

### AC-005：分类和稳定分页

- 四个 Tab 返回正确类型；
- 默认、刷新、前进和后退恢复正确 Tab；
- 每页 `20` 条并按稳定倒序；
- 多页数据无重复遗漏；
- 非法、跨用户和跨分类游标被拒绝。

### AC-006：未读和单条已读

- 新通知默认未读；
- 单条点击后幂等标记已读；
- 目标已不存在时仍可标记已读；
- 未读数量保持准确且非负。

### AC-007：一键已读

- 一键已读覆盖当前用户全部分类和未加载页面；
- 操作成功后服务端未读数为 `0`；
- 重复操作安全；
- 失败时不伪造成功状态。

### AC-008：全局未读徽标

- 各现有页面左侧通知入口显示一致未读状态；
- `1～99` 显示准确数字，超过显示 `99+`，`0` 不显示；
- 未登录不请求私有未读数量；
- 徽标具备可访问名称。

### AC-009：通知行和目标跳转

- 通知展示头像、昵称、动作、时间、未读状态和适用缩略图；
- 评论预览最多两行；
- 笔记通知进入详情，关注通知进入公开主页；
- 时间同时具备相对表达和准确辅助信息。

### AC-010：目标失效降级

- 评论删除后不显示已删除正文，并可进入仍存在的笔记；
- 笔记不存在时显示明确不可用提示；
- 单条失效不导致整页失败；
- 失效通知仍可标记已读。

### AC-011：加载、空、失败和竞争

- 首次和切换 Tab 的骨架稳定显示约 `300ms`；
- 四个空状态文案正确；
- 首次失败和加载更多失败可以安全重试；
- 快速切换 Tab 时旧响应不覆盖当前状态。

### AC-012：自适应与滚动

- 支持范围内连续自适应；
- `960×600` 下内容可访问；
- 空或少量通知不产生 HTML 根元素假滚动；
- 长列表正常滚动且不存在双重滚动、横向溢出或裁切。

### AC-013：可访问性

- Tab、通知行、一键已读、重试和加载更多可用键盘操作；
- 当前 Tab、已读状态和未读状态不只依赖颜色；
- 骨架、异步状态和徽标具备合理辅助技术语义。

### AC-014：安全与公开边界

- 接口不返回邮箱、Cookie、验证码或无关私密字段；
- 评论按纯文本安全显示，删除后不再返回正文；
- 通知和游标不能跨用户枚举；
- OpenAPI 成功和错误响应与真实接口一致。

### AC-015：既有功能回归

- 点赞、收藏、评论和关注既有业务闭环保持正确；
- 首页、详情、个人主页、公开主页和搜索页导航无直接回归；
- 常规静态检查、单元/集成测试、构建、数据库校验及适用 Browser E2E 通过。

## 19. 明确允许延后

- 实时通知和长连接；
- Redis 未读缓存；
- 事件总线、消息队列和异步投递；
- 多人互动聚合；
- 系统、运营、审核、私信、回复和 `@` 通知；
- 通知设置、免打扰和推送渠道；
- 通知删除、归档、过期和历史清理；
- 生产容量指标明确后的性能优化。

## 20. 风险

- 在既有互动服务中增加事务通知写入可能影响 SPEC-007，需要完整验证原有幂等和权限行为；
- 页面外壳在多个路由复用不完全统一，未读徽标接入时需避免复制出不一致逻辑；
- 评论真实删除与通知保留需要正确的可空关系和正文删除边界；
- 通知长期不自动过期会增长数据量，当前以索引和游标控制，后续依据生产指标复审；
- 相对时间、分页和异步已读状态存在请求竞争，需要显式处理旧响应和失败回滚；
- 本期拉取式交付不保证实时，用户需通过进入、刷新或导航获取最新状态。
