## 1. 背景

当前登录弹窗要求用户勾选“我已阅读并同意《用户协议》《隐私政策》”，但两个入口仍提示“功能开发中”，后端只接收一个布尔值，无法证明用户同意的具体文档版本和时间。侧边栏“更多”和“关于我们”同样尚未提供实际功能。

本 Spec 将建立可公开访问、内容完整且可维护的用户协议与隐私政策，记录用户同意版本和时间，为实质更新提供重新确认机制，并完善侧边栏“更多”“关于我们”和帮助反馈入口。

法律页面属于项目提供的信息文本，不代表已经完成全部运营许可、备案、个人信息出境或其他法定程序。正式公开运营前仍应由具备相应资质的法律专业人士结合实际主体、服务器所在地、第三方服务和运营模式复核。

## 2. 目标

- 交付公开可访问的《用户协议》和《隐私政策》页面；
- 让登录、注册和重新认证弹窗中的条款入口真实可用；
- 在不丢失登录表单内容的前提下允许用户阅读条款；
- 由后端记录用户实际接受的协议版本、隐私政策版本和接受时间；
- 对发生实质更新的文档要求现有用户重新确认；
- 使用不纳入 Git 的结构化本地 JSON 保存运营主体等资料；
- 完善“更多”菜单、帮助与反馈页面以及“关于我们”页面；
- 保持现有桌面 Web、自适应、认证、安全和可访问性基线。

## 3. 范围

### 3.1 包含

- `/terms` 用户协议公开页面；
- `/privacy` 隐私政策公开页面；
- `/help` 帮助与反馈公开页面；
- `/about` 关于我们公开页面；
- 登录、注册和重新认证场景中的可点击条款链接；
- 版本化条款接受记录；
- 已登录用户的条款状态检查和实质更新后的重新确认；
- 侧边栏“更多”弹出菜单及登录态差异；
- 侧边栏“关于我们”真实导航；
- 本地结构化法律资料配置、示例配置、校验和 Docker 只读挂载约定；
- 数据库兼容迁移、后端接口、OpenAPI、前端测试和正式 Browser E2E。

### 3.2 不包含

- 律师出具的法律意见、合规认证或备案代办；
- ICP 许可或备案、公安备案、个人信息出境申报、标准合同或认证流程；
- 未满 14 周岁用户及其监护人同意流程；
- 实名认证、身份证件、监护关系核验或年龄真实性核验；
- 站内客服、工单系统、在线聊天客服或客服后台；
- 用户自行注销账号的产品闭环；
- Cookie 偏好中心、广告追踪同意平台或第三方统计 SDK；
- 条款内容管理后台、富文本编辑器或在线发布系统；
- 多语言条款；
- App 端。

## 4. 法律资料配置与隐私边界

### 4.1 文件约定

- 真实资料保存在 `frontend/config/legal.local.json`；
- `legal.local.json` 必须被 `.gitignore` 忽略，不得纳入 Git、构建上下文、日志、测试快照或错误详情；
- 仓库只提交 `frontend/config/legal.example.json`，其中只包含字段说明和明显的占位值；
- 仓库提交一个服务端专用 TypeScript 配置加载器，负责在运行时读取和校验 JSON；
- 法律页面必须由 Next.js 服务端动态渲染；真实资料不得使用 `NEXT_PUBLIC_` 环境变量，也不得进入客户端 JavaScript 包；
- 本地开发从 `frontend/config/legal.local.json` 读取；
- Docker 生产运行时将服务器本地的真实配置只读挂载至 `/app/frontend/config/legal.local.json`；
- 正式 Docker 镜像不得内置真实配置，服务器上的真实配置不得通过 GitHub 仓库传输；
- 文件缺失、JSON 非法、字段为空、邮箱格式非法、日期格式非法或仍使用示例占位值时，服务端必须返回受控的“法律信息暂不可用”状态并记录不含真实值的错误；生产就绪检查必须失败，不能以占位内容静默上线。

### 4.2 首期结构

结构至少表达以下信息，字段命名可以在不改变语义的前提下由实施 Agent 细化：

```json
{
  "operator": {
    "displayName": "请填写运营主体"
  },
  "contact": {
    "email": "请填写联系邮箱"
  },
  "legal": {
    "governingLaw": "CN_MAINLAND",
    "effectiveDate": "YYYY-MM-DD"
  }
}
```

- 运营主体名称、联系邮箱、适用法律和生效日期的真实值已由用户在对话中提供，但不得复制到任何版本化项目文件；
- `governingLaw` 首期只接受代表中国大陆法律的受控枚举值；
- `effectiveDate` 使用 `YYYY-MM-DD` 纯日期；
- 文档版本号不是隐私资料，由后端版本化常量管理并纳入 Git；
- 只有发生需要用户重新确认的实质变更时才提升对应文档版本；错别字、排版和不改变权利义务的澄清不提升版本；
- 未来增加服务器区域、第三方处理者或其他法律元数据时，应扩展结构并保持旧配置错误可诊断，不把真实资料改回硬编码或环境变量。

### 4.3 可见性说明

- 真实资料不在 GitHub 源码或客户端 JavaScript 中公开；
- 用户访问法律页面时，运营主体名称和联系邮箱必须出现在最终 HTML 中，这是法律页面的正常公开信息；
- API、日志和错误响应不得额外暴露本地配置文件路径、文件内容或服务器目录结构。

## 5. 文档页面与导航

### 5.1 公共访问

- `/terms`、`/privacy`、`/help` 和 `/about` 均无需登录即可访问；
- 页面沿用小蓝书蓝色品牌视觉、现有左侧导航和桌面 Web 自适应基线；
- 法律正文使用适合长文阅读的单列内容区，提供清晰标题、目录、章节层级、更新时间/生效日期和返回入口；
- 支持键盘访问、可见焦点、语义化标题层级和浏览器原生文本选择；
- 在最低支持视口 `960×600` 下内容不得被裁切，长文由主内容区自然滚动，不产生双重滚动或无内容假滚动；
- 低于最低支持宽度时仍保持内容可访问，不要求完整桌面比例。

### 5.2 条款链接行为

- 登录、注册和重新认证弹窗中的《用户协议》《隐私政策》必须使用真实链接；
- 从弹窗点击时在新的浏览器标签页打开对应页面，原标签页的邮箱、验证码、昵称、勾选状态和弹窗步骤保持不变；
- 打开条款页面本身不代表同意；只有用户主动勾选并完成后端接受流程才形成记录；
- 链接不可被勾选框或标签点击行为误触发，键盘可分别聚焦和打开；
- “更多”菜单中的法律入口同样打开新标签页。

## 6. 用户协议内容要求

首版《用户协议》必须使用清晰中文并至少覆盖：

1. 协议范围、生效方式、运营主体和联系方式；
2. 服务定位、Web 端服务范围及功能可能调整的说明；
3. 账号注册、邮箱验证、会话安全和用户保管责任；
4. 用户须年满 14 周岁；未满 14 周岁不得注册或使用当前版本服务；
5. 昵称、头像、笔记、评论、私信等用户内容和行为规范；
6. 禁止违法、有害、侵权、欺诈、骚扰、恶意自动化、破坏安全或滥用服务的行为；
7. 用户对其发布内容保留原有知识产权；
8. 用户授予小蓝书非独占、免费的必要使用许可，仅用于内容存储、复制、展示、分发、提供功能和产品宣传；
9. 用户删除内容后停止新增使用，但法律要求留存、已形成的合理缓存/备份和删除前已完成的宣传材料除外；
10. 投诉、删除、限制功能、暂停账号和终止服务的基本处理原则；
11. 服务中断、不可抗力、第三方服务和责任限制，但不得排除依法不能排除的责任；
12. 协议修改、实质更新重新确认和停止使用的选择；
13. 适用中国大陆法律，争议先协商，协商不成时向依法有管辖权的人民法院提起诉讼；
14. 联系方式和生效日期。

协议不得声称小蓝书已经取得尚未取得的许可、备案、认证或资质，不得使用绝对免责、无限授权或与本 Spec 相冲突的格式条款。

## 7. 隐私政策内容要求

首版《隐私政策》必须依据当前已实现功能如实描述，不得承诺尚未实现的技术能力，并至少覆盖：

1. 个人信息处理者、联系邮箱、生效日期和适用范围；
2. 账号信息：邮箱、昵称、小蓝书号、会话及验证码处理；
3. 个人资料：头像、性别、出生日期、派生年龄、年龄公开状态和简介；
4. 用户内容：笔记、媒体、频道、评论、回复、点赞、收藏、关注和通知；
5. 私信内容、会话关系、已读状态和客户端幂等标识；
6. 设备与运行数据：必要的 IP、请求日志、Cookie、会话标识和匿名浏览去重标识；
7. 每类信息的处理目的、处理方式、必要性和主要保存规则；
8. 邮箱验证码、会话和匿名浏览 Cookie 的用途与已确认生命周期；
9. 网易 163 SMTP、服务器/托管基础设施等必要服务提供者类别，不虚构当前不存在的广告、画像或统计用途；
10. 当前不出售个人信息，不为广告建立用户画像，不把 Redis 用作本 Spec 的新增缓存；
11. 信息共享、委托处理、转移、公开披露和依法提供的边界；
12. 安全措施、访问控制、最小化、备份、事件处置及无法保证绝对安全的合理说明；
13. 用户查阅、复制、更正、补充、删除、撤回同意和提出请求的方式；当前没有站内入口的请求通过公开联系邮箱受理并进行必要身份核验；
14. 年满 14 周岁的使用门槛，以及发现未满 14 周岁信息后的停止处理和删除/匿名化原则；
15. 政策更新、实质更新重新确认和历史接受记录；
16. 数据存储或跨境处理必须按实际部署如实披露，不得仅凭页面文本声称已完成个人信息出境合规程序；
17. 联系方式和投诉渠道。

当前已确认的初期生产服务器位于境外，因此正式上线前必须结合具体服务器国家/地区、处理活动和服务商完成单独法律评估。该评估及法定程序不属于本 Spec 的开发验收范围，但隐私政策不得作与实际部署相反的陈述。

## 8. 年龄规则

- 首期服务只允许年满 14 周岁的用户注册和使用；
- 勾选协议代表用户同时声明自己已经年满 14 周岁；
- 不增加身份证、实名或监护关系核验；
- 个人资料出生日期不得设置为会使当前年龄小于 14 周岁的日期；
- 年龄按现有服务端纯日期规则计算，生日当天视为已满相应年龄；
- 保存不满足年龄门槛的出生日期时，后端拒绝整个资料更新并返回稳定字段错误；
- 如果历史数据或异常数据表明用户未满 14 周岁，系统不得继续公开其资料或允许新增内容和互动，应进入受限状态并提示通过联系邮箱处理；
- 本 Spec 不实现监护人同意，因此不得通过勾选框绕过年龄门槛。

## 9. 版本化接受与重新确认

### 9.1 当前版本来源

- 后端是当前用户协议版本和隐私政策版本的唯一权威来源；
- 前端不得自行决定当前版本，也不得通过客户端传入任意版本让后端直接信任；
- 后端公开返回当前文档版本、是否需要当前用户重新确认和法律页面 URL；
- 文档版本使用稳定、可比较且不可复用的标识；旧版本号不得重新指向不同正文。

### 9.2 接受记录

- 每次有效接受至少记录：用户 ID、用户协议版本、隐私政策版本、服务端接受时间和接受场景；
- 接受场景区分新用户注册、已有用户登录、已登录会话重新确认；
- 接受记录采用可追踪历史记录，不因后续接受新版本而覆盖或删除旧记录；
- 不把勾选框布尔值本身当作唯一接受证据；
- 不保存条款页面浏览历史；
- 接受时间由服务端生成，不能信任客户端时间。

### 9.3 登录和注册

- 获取验证码时仍要求勾选条款；
- 后端在验证码挑战中绑定当时的权威协议版本，而不是信任客户端版本；
- 验证码最终验证成功后才把接受记录关联至已有用户或新创建用户；
- 仅发送验证码、验证码失败、挑战过期或注册未完成均不得创建用户接受记录；
- 条款版本在验证码挑战期间发生变化时，旧挑战不能接受新版本，用户必须重新确认并获取新的验证码；
- 登录或注册成功时返回的会话必须已经满足当前版本要求。

### 9.4 已登录会话重新确认

- 文档发生实质更新并提升版本后，已有会话在恢复或下一次受保护请求时被识别为待重新确认；
- 前端显示不可忽略的重新确认对话框，提供两个文档的新标签页链接、“同意并继续”和“退出登录”；
- 未确认期间允许读取法律、帮助和关于页面，并允许退出登录；
- 未确认期间不得发布、互动、修改资料、发送私信或执行其他需要登录的写操作；
- 用户确认后由后端记录当前两个版本和服务端时间，原会话恢复正常；
- 只发生非实质文字修订且版本未提升时，不要求重新确认；
- 接受接口必须幂等，并发重复提交至多形成一条相同版本、相同场景的有效记录。

## 10. “更多”菜单

- 点击侧边栏“更多”打开锚定于该按钮附近的弹出菜单，不再显示“功能开发中”；
- 菜单使用 `menu`/`menuitem` 语义，支持方向键或 Tab、Enter/Space、Escape、点击外部关闭和关闭后的焦点恢复；
- 未登录状态依次显示：帮助与反馈、用户协议、隐私政策；
- 已登录状态依次显示：编辑资料、帮助与反馈、用户协议、隐私政策、退出登录；
- “编辑资料”导航到 `/settings/profile`；
- “帮助与反馈”导航到 `/help`；
- 两个法律入口在新标签页打开；
- “退出登录”复用现有后端退出语义，只结束当前设备会话；请求期间防止重复提交，失败时保留登录状态并显示错误；
- 菜单与现有个人身份菜单可以同时提供编辑资料和退出登录，不删除既有入口；同一时间只能有一个弹出菜单处于打开状态。

## 11. 帮助与反馈

- `/help` 首期提供静态常见问题，不建立后端工单数据；
- 常见问题至少覆盖：获取不到邮箱验证码、登录状态、发布笔记、频道、点赞收藏评论关注、通知、私信、编辑资料、隐私与条款；
- 答案必须与当前已实现功能一致，不宣传尚未实现的能力；
- 页面提供“前往 GitHub Issues 反馈”外部链接，目标为当前项目仓库的新建 Issue 页面；
- 页面提示 GitHub Issues 属于公开渠道，不应提交邮箱验证码、授权码、会话 Cookie、身份证件、私信内容或其他敏感信息；
- 页面同时展示由本地法律配置提供的联系邮箱，作为隐私和法律请求渠道；
- 外部链接在新标签页打开，并具备可访问名称和安全的 `rel` 属性。

## 12. 关于我们

- 侧边栏“关于我们”不再提示“功能开发中”，而是导航到 `/about`；
- 页面说明产品名称“小蓝书”、Web 内容社区定位、聚焦男性社区的产品方向和当前主要能力；
- 页面不得记录或暗示未来必须交付 App 端；
- 页面展示小蓝书 Logo、用户协议、隐私政策、帮助与反馈入口；
- 页面展示运营主体和联系邮箱，但从本地法律配置动态读取；
- 不展示虚构团队成员、公司地址、备案号、许可证、合作伙伴或运营数据。

## 13. 错误、安全与兼容性

- 所有法律状态和接受接口遵守现有 HttpOnly Cookie 会话、CSRF/Origin 和统一错误响应边界；
- 未登录用户不能写入接受记录；登录/注册挑战完成时除外，由后端在可信认证事务中关联；
- 任何用户都不能读取其他用户的接受记录；首期不提供用户侧接受历史页面；
- 迁移不得破坏现有用户、会话、内容、互动或私信；

## 15. 验收标准

### AC-001：本地配置不进入版本控制

- 仓库只包含示例 JSON、配置模式/加载器和忽略规则；
- `legal.local.json` 的真实值不出现在 Git 差异、构建产物客户端包、测试快照或日志中；
- 缺失、非法和占位配置均产生受控错误，生产就绪检查失败；
- Docker 镜像不内置真实资料，运行时只读挂载后页面正确显示配置值。

### AC-002：法律页面

- `/terms` 和 `/privacy` 无需登录即可访问；
- 页面显示正确文档标题、版本、生效日期、运营主体和联系邮箱；
- 用户协议覆盖第 6 节全部主题，隐私政策覆盖第 7 节全部主题；
- 页面内容与当前功能一致，不包含虚构资质、功能或绝对合规承诺；
- 配置错误时不显示示例值或泄露文件信息。

### AC-003：登录弹窗条款入口

- 首页登录弹窗、共享登录弹窗和重新认证弹窗中的两个条款入口都可用；
- 点击后在新标签页打开正确页面；
- 原标签页的输入内容、弹窗步骤和勾选状态不丢失；
- 打开页面不自动勾选，也不创建接受记录。

### AC-004：版本权威与验证码挑战

- 后端返回当前版本并判断用户是否需要重新确认；
- 客户端不能伪造或降级当前版本；
- 获取验证码时把后端当前版本绑定到挑战；
- 失败、过期或未完成挑战不创建接受记录；
- 挑战期间版本变化后必须重新确认和获取验证码。

### AC-005：注册与登录接受记录

- 新用户注册、已有用户登录成功时分别形成准确场景的历史接受记录；
- 记录包含用户、两个版本和服务端时间；
- 登录/注册会话建立时已满足当前版本；
- 重试和并发不会生成重复的同版本同场景有效记录；
- 其他用户不能读取该记录。

### AC-006：实质更新重新确认

- 提升任一当前文档版本后，旧接受记录对应的已登录会话进入待确认状态；
- 重新确认对话框不可被普通关闭操作绕过；
- 未确认时法律/帮助/关于页面和退出登录可用，认证写操作被后端拒绝；
- 同意后记录新版本并恢复当前会话；退出登录不会形成新接受记录；
- 非实质修改且版本未变化时不触发重新确认。

### AC-007：年龄门槛

- 协议清楚说明用户须年满 14 周岁；
- 登录/注册勾选行为包含年龄声明；
- 出生日期形成未满 14 周岁年龄时，前后端均阻止保存，后端为最终权威；
- 生日当天边界正确；历史异常数据进入受限状态，不继续公开资料或允许认证写操作。

### AC-008：“更多”菜单

- “更多”不再提示开发中，菜单锚定、层级和关闭行为正确；
- 登录前后菜单项、顺序和导航符合第 10 节；
- 编辑资料和退出登录复用现有能力；
- 键盘操作、焦点循环/关闭恢复和同一时间单菜单规则通过。

### AC-009：帮助、反馈与关于页面

- `/help` 和 `/about` 无需登录即可访问；
- FAQ 与现有功能一致，GitHub Issues 链接和敏感信息警告正确；
- “关于我们”侧栏入口真实导航并显示已确认产品定位；
- 两页正确使用本地配置中的公开主体和联系邮箱，不展示虚构资料。

### AC-010：迁移、兼容与安全

- 空库部署和从 SPEC-011 历史库升级均成功，旧用户、内容、互动、通知和私信无损；
- 当前会话、登录、注册、重新认证和退出登录回归通过；
- 配置读取、接口权限、错误响应和日志不泄露真实配置或其他用户接受记录；
- OpenAPI 与真实响应一致。

### AC-011：自适应与可访问性

- 四个新页面在 `960×600` 及更大连续视口中无裁切、双重滚动和假滚动；
- 长文、菜单和重新确认对话框支持完整键盘访问及正确语义；
- 新标签页、焦点恢复和重新确认门禁在 Chromium 通过完整流程，并在 Firefox、WebKit 完成差异风险验证。

### AC-012：分层回归

- 定向测试覆盖配置解析、版本绑定、接受记录、年龄边界、写操作门禁、菜单和页面；
- 前后端静态检查、单元/集成测试和生产构建通过；
- 实施阶段运行相关 Chromium E2E，初次独立验收运行一次完整 Browser E2E；
- 常规 CI 配置仍为手动触发且不安装浏览器、不运行 Browser E2E；
- 测试产物、临时配置和一次性脚本按项目规则清理，真实本地配置绝不复制进测试目录。
