## 1. 背景

小蓝书已经支持用户关注、取消关注、查看自己的关注名单、访问公开主页、接收关注通知，以及在互相关注后发送私信。但关注关系还没有形成完整的内容消费和关系查看闭环：用户不能集中浏览所关注账号的笔记，不能查看粉丝名单，也不能从他人主页查看公开关注与粉丝关系。

本 Spec 建立首页【关注】信息流，补齐自己和他人的关注、粉丝列表，并在这些列表中提供服务端权威的关注、回关与取消关注操作。推荐算法、关系推荐和复杂关系管理继续延后。

## 2. 已确认目标

- 首页频道栏最左侧增加【关注】，顺序为【关注】【推荐】【数码】……；
- 【关注】仍属于首页状态，不建立独立页面；
- 关注信息流同时展示图文和视频，按笔记原发布时间倒序；
- 关注后可以看到对方当前全部可见历史笔记，不只展示关注后的内容；
- 未登录点击【关注】打开现有登录模态框，不请求信息流或展示模拟内容；
- 当前用户可以查看自己的【关注】和【粉丝】列表；
- 公开主页的【关注】和【粉丝】数量可以点击查看公开关系列表，未登录也可查看；
- 粉丝列表支持【回关】【已关注】及【互相关注】状态；
- 关系列表支持服务端权威的关注、回关和取消关注；
- 所有信息流、列表、统计与操作继续遵守拉黑、封禁、年龄限制和内容治理规则；
- 不新增推荐算法、实时推送或新的关注通知类型。

## 3. 范围

### 3.1 本期包含

- 首页【关注】入口、URL 状态、加载和返回恢复；
- 登录用户关注账号的图文/视频混合信息流；
- 关注信息流稳定游标分页和加载更多；
- 无关注关系与已关注但无内容的差异化空状态；
- 当前用户粉丝列表；
- 当前用户现有关注列表扩展为统一关系列表体验；
- 他人公开主页的公开关注和粉丝列表；
- 关系列表中的关注、回关、取消关注和互关标识；
- 页面统计与实际可访问列表的一致性；
- 关注关系变化对信息流、私信资格和现有通知的联动；
- 拉黑、封禁、年龄限制、内容隐藏与删除的统一过滤；
- REST/OpenAPI、必要索引、前后端测试和相关 Browser E2E。

### 3.2 本期不包含

- 个性化推荐、关注推荐、好友推荐或搜索行为排序；
- 关注分组、备注、特别关注、批量关注或批量取消；
- 关系列表内搜索、筛选或自定义排序；
- 移除粉丝、强制单向断开关系或关注请求审批；
- 私密账号、仅好友可见关系或用户自定义关系隐私；
- 关注信息流实时推送、自动插入或 WebSocket 刷新；
- “互相关注成功”通知、取消关注通知或关系变更邮件；
- 陌生人私信、群聊或对现有互关私信规则的改变；
- Redis 关系缓存、消息队列、搜索引擎或常规 CI Browser E2E。

## 4. 用户、权限与公开边界

### 4.1 未登录用户

- 可以继续浏览推荐、频道、视频、搜索、公开主页和公开关系列表；
- 点击首页【关注】时打开现有登录模态框；
- 未登录状态不得请求认证关注信息流，不显示缓存的上一位用户数据或演示数据；
- 可以从他人公开主页查看该用户可公开的关注和粉丝列表；
- 点击关系列表中的【关注】或【回关】时打开登录模态框，不提前改变按钮状态。

### 4.2 登录用户

- 可以浏览自己的关注信息流；
- 可以查看自己与其他公开用户的关注和粉丝列表；
- 可以在列表中关注、回关和取消关注，但不能关注自己；
- 关注写操作继续要求有效会话、当前条款版本和年龄门禁；
- 取消关注后历史私信仍可读，但失去互关时不能继续发送。

### 4.3 目标用户与服务端权威

- 目标用户 ID、列表所有者、查看者身份和关系状态全部由服务端校验；
- 被拉黑、封禁、年龄受限、已删除或按治理策略不可公开的账号不返回；
- 笔记隐藏、删除、作者封禁和双方拉黑必须在服务端过滤，不依赖前端移除；
- 公开关系列表不返回邮箱、完整出生日期、内部对象 Key、账号状态原因或后台治理信息；
- 非公开或不可访问目标统一使用不泄露具体原因的现有安全响应。

## 5. 首页【关注】入口与 URL

- 首页频道栏最左侧增加【关注】，其后依次为【推荐】和现有公开频道；
- 【关注】是信息流类型，不是数据库频道，不参与发布选择、频道管理或频道详情；
- 关注状态使用 `/?feed=following` 表达；推荐继续使用 `/`，频道继续使用既有 `/?channel=<code>`；
- `feed=following` 与 `channel` 同时出现时使用明确的互斥规范化策略，不允许页面同时显示两个选中项；
- 刷新、前进、后退和复制 URL 后保持【关注】状态；
- 已登录用户从其他页面返回时遵守现有列表与滚动恢复规则；
- 未登录直接访问 `/?feed=following` 时保留该地址并打开登录模态框，登录成功后加载关注信息流；关闭登录框后不得伪装为已加载。

## 6. 关注信息流数据规则

- 只允许有效登录用户访问关注信息流接口；
- PostgreSQL `UserFollow` 与公开笔记数据是唯一真实来源，不使用 Redis 缓存；
- 返回当前用户所关注账号当前全部可见笔记，包括关注关系建立前发布的内容；
- 图文和视频混合展示，复用首页现有笔记卡片、视频图标、时长、浏览量和互动状态；
- 按 `Note.createdAt DESC, Note.id DESC` 或等价稳定顺序排序；
- 编辑只更新编辑状态，不改变原发布时间或重新置顶；
- 每页固定 `20` 条，使用绑定当前用户和 `following` 范围的不透明游标；
- 游标篡改、跨用户或跨信息流复用返回稳定错误，不回退为推荐内容；
- 取消关注后目标账号全部笔记从后续权威响应中消失；重新关注后其可见历史笔记重新出现；
- 用户停留期间不自动插入新笔记，刷新、重新进入或再次切换到【关注】时获取最新内容。

## 7. 关注信息流状态与交互

- 首屏使用与推荐信息流尺寸一致的稳定骨架，最短可感知展示沿用既有信息流策略；
- 滚动接近底部时自动加载下一页；
- 加载更多失败保留已加载内容，并提供可访问的重试操作；
- 请求失败不得显示推荐内容、旧账号缓存或本地演示卡片；
- 用户尚未关注任何有效账号时显示“关注感兴趣的用户，发现他们的最新内容”，并提供进入用户搜索的按钮；
- 已关注有效账号但当前没有任何可见笔记时显示“关注的人还没有发布笔记”；
- 信息流只因内容或关系数据真正可继续分页时显示加载状态，不制造根元素假滚动；
- 取消关注导致当前信息流内容变化时，下次请求和重新进入必须以服务端状态为准；当前已渲染详情或卡片不得继续允许越权互动。

## 8. 关系列表类型与入口

### 8.1 当前用户个人主页

- 【关注】和【粉丝】统计都改为可访问按钮；
- 点击后在当前页面打开统一关系列表模态框，不跳转独立 URL；
- 标题分别为【我的关注】与【我的粉丝】；
- 关闭后焦点返回对应统计按钮，个人主页滚动位置保持。

### 8.2 他人公开主页

- 【关注】和【粉丝】统计对匿名及登录查看者均可点击；
- 点击后打开同一统一模态框，标题为【TA 的关注】或【TA 的粉丝】；
- 列表所有者在加载期间不可访问时，模态框显示安全失败状态并允许关闭，不泄露封禁或拉黑原因；
- 公开主页原有资料、笔记列表和关注按钮布局继续保持。

### 8.3 模态框通用规则

- 每页 `20` 人，使用稳定不透明游标；
- 关注列表按关系 `createdAt DESC, followedId DESC` 或等价稳定顺序；
- 粉丝列表按关系 `createdAt DESC, followerId DESC` 或等价稳定顺序；
- 首屏展示稳定用户行骨架，支持空、失败、重试和加载更多；
- 列表区域独立滚动，不制造 HTML 根元素假滚动或双重滚动；
- 加载更多失败保留已有用户；前端按用户 ID 去重；
- 头像、昵称和用户主体进入公开主页，关系按钮只处理关注状态。

## 9. 用户行与关系状态

- 每行至少展示头像、昵称、小蓝书号和公开个人简介；
- 自己的行不得显示关注按钮，使用稳定的【我】标识或无操作状态；
- 其他用户根据当前查看者关系展示：
  - 未关注：`关注`；
  - 对方是当前用户的粉丝且当前用户未关注：`回关`；
  - 当前用户已关注：`已关注`；
  - 双方互相关注：在【已关注】之外显示明确的`互相关注`关系标识；
- 未登录查看公开列表时，非本人行显示可触发登录模态框的【关注】；
- 本期不在用户行增加私信、举报、拉黑、备注或更多菜单；
- 长昵称、小蓝书号和简介正确截断，不挤压关系按钮或状态标识。

## 10. 关注、回关与取消关注

- 关注和回关复用现有幂等目标状态接口，成功后以服务端权威结果更新；
- 【已关注】按钮可以发起取消关注，继续使用明确确认对话框；
- 取消关注确认、忙碌、错误、Escape 和焦点恢复沿用 SPEC-014；
- 操作成功后同步更新当前行、其他已加载相同用户行、页面统计和当前用户关系状态；
- 取消关注不提供撤销按钮，也不主动删除当前用户的粉丝关系；
- 本期不提供【移除粉丝】，用户需要隔离对方时继续使用拉黑；
- 目标在操作期间被封禁、拉黑、删除或变为不可访问时，前端按服务端结果安全移除或降级该行；
- 请求失败保留当前行、已有列表和原按钮状态，不显示虚假成功；
- 多窗口重复关注、回关或取消关注必须幂等收敛；
- 不能通过篡改列表所有者、目标 ID 或游标绕过自关注、拉黑或封禁门禁。

## 11. 统计一致性

- 当前用户和公开主页的【关注】【粉丝】数量必须与同一查看者实际可访问的对应列表一致；
- 统计排除双方拉黑、目标封禁、年龄限制、账号删除和其他不可公开关系目标；
- 不向普通用户解释数量减少的具体过滤原因；
- 管理员恢复账号后，未被删除的关注关系可以重新展示并计数；
- 拉黑已经原子删除的关注关系在解除拉黑后不会自动恢复；
- 关注或取消关注成功响应应提供足以更新当前用户统计的权威结果，不能只依赖前端 `+1/-1` 推测；
- 并发关系变化后刷新必须从数据库恢复正确数量。

## 12. 通知与私信联动

- 新关注继续产生现有关注通知；
- 取消关注不发送通知，也不删除历史关注通知；
- 取消后重新关注属于新的关注关系，可以产生一条新的关注通知；
- 不新增“互相关注成功”、取消关注或关系恢复通知类型；
- 关注、回关、取消关注继续实时影响 SPEC-011 的互关私信发送资格；
- 失去互关后历史会话和消息仍可读，发送入口禁用；恢复互关后原会话恢复发送；
- 本期不通过 WebSocket 推送关系列表、主页统计或关注信息流变化。

## 13. 拉黑、封禁与治理联动

- SPEC-015 的方向性拉黑继续形成双方关系、内容、互动和私信隔离；
- 拉黑时双方关注关系被原子删除，因此两人不再出现在彼此的关注、粉丝列表或关注信息流；
- 解除拉黑不恢复关注、历史通知或私信发送资格；
- 被封禁账号及其笔记不出现在关注信息流和普通用户关系列表；
- 账号恢复后，封禁期间未删除的关注关系和未单独隐藏的笔记按数据库状态重新可见；
- 管理员隐藏、作者删除或媒体鉴权失败的笔记不得通过关注信息流旧 ID 或缓存继续访问；
- 列表和统计过滤不得泄露账号被谁拉黑、被何种理由封禁或内容为何隐藏。

## 14. API 与错误契约

建议在实施阶段按现有模块边界提供下列等价接口，具体路径可以在不改变行为的前提下局部调整，但 OpenAPI 必须一致：

- `GET /notes/following?cursor=...&limit=20`：当前用户关注信息流；
- `GET /users/:userId/following?cursor=...`：目标用户公开关注列表；
- `GET /users/:userId/followers?cursor=...`：目标用户公开粉丝列表；
- 当前用户列表可以复用公开接口的 `me` 解析或保留兼容的 `/profile/me/following`，但不得出现行为不一致的两套实现；
- 现有 `PUT /users/:userId/follow` 与 `DELETE /users/:userId/follow` 继续作为关系写入口。

错误语义：

- `401`：关注信息流或写操作未登录、会话失效；
- `404`：列表所有者、目标用户或内容不存在/不可访问，或按安全策略不应泄露；
- `400/422`：游标、limit 或 URL 状态不合法；
- `409`：当前状态与目标操作不兼容且不能安全幂等收敛；
- 失败响应使用稳定中文消息和业务码，不返回 SQL、堆栈、Cookie、对象 Key、邮箱或治理内部原因。

## 15. 数据、查询与性能

- PostgreSQL `UserFollow` 是关系、关系时间和排序的唯一真实来源；
- 不为本期新增 Redis 关系缓存或信息流缓存；
- 关注信息流查询必须由数据库联结或可证明等价的批量查询完成，不允许先加载全部关注 ID 再无界拉取笔记；
- 关系列表的公开资料、当前查看者关注状态和互关状态必须批量获取，禁止逐行 N+1；
- 每个接口最多返回 `20` 条，数据库多取一条判断下一页；
- 游标绑定列表类型、列表所有者和查看者安全范围，不能跨列表复用；
- 现有 `UserFollow` 关注侧索引继续复用；实施前必须用查询计划确认粉丝侧是否需要 `(followedId, createdAt DESC, followerId DESC)` 索引；
- 如需新增索引，必须通过无损迁移建立，不改写历史关系时间；
- 删除或取消关系后的分页可以少一项，但不得无限重复、越权补位或返回错误用户。

## 16. 前端状态、缓存与并发

- 首页推荐、频道和关注信息流使用明确分离的状态与请求键；
- 登录用户切换账号、退出、会话失效或封禁时必须清空内存中的关注信息流和私人关系状态；
- 匿名公开关系列表不得继承上一位登录用户的按钮关系状态；
- 关注操作完成后同步当前已加载页面，但刷新仍以服务端结果为准；
- 同一用户出现在多个已打开模态框或页面时，不要求跨标签页实时广播，但每次重新加载必须收敛；
- 新请求开始前取消或忽略旧请求响应，避免快速切换列表所有者后显示错人的关系；
- 加载失败保留同一请求范围已有内容，不保留其他用户的数据伪装成功。

## 17. 自适应与可访问性

- 最低支持范围继续为 `960×600 CSS px`，范围内连续自适应；
- 首页新增【关注】后频道栏允许自然横向滚动或既有等价策略，不挤压搜索和主内容；
- 关注信息流空状态、一行卡片和加载更多不制造根元素假滚动；
- 关系列表模态框在 `960×600` 下标题、列表、按钮和关闭操作全部可达；
- 对话框打开时焦点进入，Tab 不逃逸，Escape 只关闭未提交对话框，关闭后恢复触发焦点；
- 关系状态不能只依赖颜色；加载、错误、成功和忙碌状态可被辅助技术感知；
- `prefers-reduced-motion` 下不依赖动画表达状态；
- Chromium 覆盖主流程，Firefox/WebKit 只覆盖模态框焦点、历史导航和滚动等浏览器差异风险。

## 18. 数据迁移与兼容性

- 优先复用现有 `UserFollow` 模型、主键和关注侧稳定排序索引；
- 只有粉丝侧查询计划证明需要时，增加兼容索引；
- 历史关注关系、创建时间、关注通知、私信会话和消息保持不变；
- 不回填、不重写或伪造历史关系时间；
- 空库应用全部迁移和从 SPEC-015 历史库升级必须成功；
- 推荐、频道、视频、搜索、详情、资料、通知、治理和笔记管理接口继续兼容；
- SPEC-014 “他人关系名单不公开”的旧规则由本 Spec 和决策 0016 明确替代。

## 19. 测试与验收策略

- 实施阶段先运行关注信息流、公开关系列表、统计、关系状态和治理过滤的定向测试；
- 初次实施完成运行受影响 lint/typecheck、定向单元/集成、生产构建和 Chromium SPEC-016 主流程；
- 初次独立验收逐项验证 AC-001 至 AC-014，并按项目规则运行一次完整 Browser E2E；
- Firefox/WebKit 只验证模态框焦点恢复、URL 历史导航、内部滚动等差异场景；
- 小范围返工只运行历史失败项和直接受影响回归，不机械重复完整 E2E；
- 常规手动 CI 不安装浏览器、不运行 Browser E2E，CI 结果不作为 Spec 完成门禁；
- 测试账号、昵称、简介和内容不得包含真实个人隐私或凭据。

## 20. 验收标准

### AC-001：首页入口与 URL

- 【关注】位于【推荐】之前，不作为发布频道；
- `/?feed=following` 刷新、前进和后退保持状态；
- 推荐、频道和关注状态互斥且无错误选中。

### AC-002：未登录门禁

- 未登录点击或直达【关注】打开现有登录模态框；
- 不请求私人信息流，不展示旧账号或演示内容；
- 登录成功后在原 URL 加载关注信息流。

### AC-003：关注信息流数据

- 图文和视频按原发布时间稳定倒序；
- 包含关注前的可见历史笔记；
- 编辑不置顶，隐藏、删除、封禁和拉黑内容不返回；
- 每页 20 条且游标不能跨用户或范围复用。

### AC-004：关注信息流状态

- 首屏骨架、加载更多、失败保留与重试正确；
- “尚未关注任何人”和“关注的人尚无笔记”使用不同空状态；
- 空状态用户搜索入口可用，不填充演示内容。

### AC-005：当前用户关系列表

- 【我的关注】【我的粉丝】均可打开；
- 排序、20 条分页、骨架、空、失败、重试和去重正确；
- 关闭恢复焦点与页面滚动位置。

### AC-006：公开关系列表

- 匿名和登录用户可查看他人公开【关注】【粉丝】；
- 列表只返回公开资料，不泄露私人或治理字段；
- 不可访问用户使用安全失败语义。

### AC-007：关系状态呈现

- 【关注】【回关】【已关注】【互相关注】与服务端关系一致；
- 当前用户本人没有自关注操作；
- 未登录点击关系操作打开登录框且不假成功。

### AC-008：关系写操作

- 关注、回关、取消关注幂等且以服务端结果为准；
- 取消关注需要确认，失败保留当前行；
- 多窗口和目标状态变化安全收敛，不出现重复关系。

### AC-009：统计一致性

- 页面关注/粉丝数量与同一查看者可访问列表一致；
- 关注操作后使用权威结果更新；
- 拉黑删除关系不恢复，封禁恢复按现存关系重新计数。

### AC-010：通知与私信

- 新关注及重新关注继续产生既有通知；
- 取消关注不通知且不删除历史关注通知；
- 互关变化立即影响私信发送资格但不删除历史会话。

### AC-011：安全与治理过滤

- 拉黑、封禁、年龄限制、隐藏与删除在信息流、列表、统计和写接口统一生效；
- 不能通过 ID、游标、旧响应或媒体 URL 绕过；
- 错误与响应不泄露内部状态。

### AC-012：查询性能与迁移

- 列表和信息流无逐行 N+1或无界加载；
- 查询计划与排序索引匹配；
- 空库及 SPEC-015 历史库迁移成功，历史关系/通知/私信无损。

### AC-013：自适应与可访问性

- `960×600` 下无关键裁切、根假滚动或双重滚动；
- 键盘可完成列表打开、关系操作、确认和关闭；
- 焦点、错误、忙碌和关系状态可感知。

### AC-014：直接回归与验证边界

- 推荐、频道、视频、搜索、主页、详情、互动、通知、私信、笔记管理和治理继续工作；
- 初次独立验收运行一次完整 Browser E2E；
- 同一最终状态不重复完整 E2E，返工仅复验失败项和受影响回归；
- 常规手动 CI 继续不运行 Browser E2E。

## 21. 风险与后续复审

- 公开社交关系会改变 SPEC-014 的隐私边界，必须统一经过治理与拉黑过滤；
- 统计若继续直接 count 全部关系会与过滤后的列表不一致，需要共享查询口径；
- 关注信息流可能随关注数和内容量增长，当前以联结、索引和游标控制，生产指标出现瓶颈后再评估扇出或缓存；
- 公开关系列表可能被批量遍历，正式运营前需要基于真实风险复审接口限流和反爬策略；
- 未来若建设私密账号、移除粉丝、关注审批、关系可见性或好友推荐，必须新建 Spec；
- 未来多实例实时信息流或关系更新需要复审消息总线，不从本期自动引入 Redis。
