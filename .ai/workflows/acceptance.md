# 独立验收工作流

## 进入条件

- 实施 Agent 已返回完整结果；
- 协调开发 Agent 已创建一个不同于实施 Agent 的验收 Agent；
- 验收 Agent 获得已确认 Spec、实施报告和必要环境信息。

## 验收原则

- Spec 是验收依据，实施报告只是辅助证据。
- 验收 Agent 不信任未经验证的“已完成”声明。
- 每项强制验收标准都需要明确结果和证据。
- CI 不作为单独的 Spec 验收项，远程 CI 运行记录不得阻塞 Spec 的本地独立验收或完成状态。
- 验收 Agent 不修改业务代码，也不在验收中顺手修复问题。
- 代码质量问题只有在违反 Spec、Constitution、已确认决策或项目规则时，才作为阻断项；其余可列为建议。

## 验收步骤

1. 阅读适用规范和已确认 Spec。
2. 检查实施差异及改动范围。
3. 将验收标准整理为逐项检查表。
4. 运行适用的自动化测试、静态检查和构建。
5. 对无法由自动化覆盖的行为进行独立验证。
6. 检查异常路径、权限、数据边界和回归风险。
7. 如需干净副本或隔离工作区，只在仓库根目录 `test/` 下创建任务专属子目录，并确保无论检查成功或失败都自动清理。
8. 输出结论、证据和临时副本清理结果，不修改业务代码。

## 结论类型

### PASS

所有强制验收标准均通过，且没有阻断性违规。

### FAIL

至少一个强制验收标准未通过，或发现违反已确认约束的问题。

报告必须包含：

- 对应验收标准；
- 可复现步骤或检查命令；
- 期望结果与实际结果；
- 影响范围；
- 证据位置；
- 建议返工边界。

### BLOCKED

由于缺少决策、环境、权限、数据或外部依赖，无法得出可靠结论。

报告必须说明：

- 已完成的检查；
- 被阻塞的验收项；
- 阻塞原因；
- 解除阻塞所需的具体条件。

## 输出

验收 Agent 使用 `.ai/prompts/result-report.md` 中的验收报告结构，将结果返回协调开发 Agent。只有协调开发 Agent 负责组织返工或向用户汇总。

协调开发 Agent 在验收 Agent 运行期间必须保持协调回合活动并持续等待。收到报告后必须先更新验收记录：`PASS` 向用户汇总并请求确认，用户确认后立即将 Spec 标记为 `Accepted` 并提供提交信息；`FAIL` 创建新的返工实施 Agent；`BLOCKED` 记录原因和解除条件并仅在确需用户或外部动作时结束回合。验收仍在运行或报告尚未处理时不得结束协调回合。

代码提交和 CI 位于 Spec 验收完成之后。默认由用户自行提交；如果提交或 CI 出错，用户将错误返回协调开发 Agent，再按实施与独立验收闭环修复，但 CI 结果本身不改变已经由用户确认完成的 Spec 状态。
