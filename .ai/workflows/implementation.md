# 实施工作流

## 进入条件

- 存在用户已确认的 Spec；
- 协调开发 Agent 已完成任务交接；
- 任务范围、验收标准和允许修改的文件范围明确；
- 没有尚未解决且会影响实施结果的关键决策。

## 任务交接

协调开发 Agent 使用 `.ai/prompts/task-handoff.md`，至少提供：

- Spec 路径及确认状态；
- 本轮实施目标；
- 范围内与范围外事项；
- 相关 Constitution、决策、规则和代码上下文；
- 允许修改的目录或文件；
- 必须运行的测试；
- Git 和外部系统授权；
- 结果返回格式。

## 单 Agent 调度规则

- 每一轮实施只允许一个实施 Agent，复杂任务也不得按前端、后端、数据库或 E2E 拆成多个并行实施 Agent。
- 协调开发 Agent 必须把该轮完整范围和必要上下文一次性交给同一个实施 Agent。
- 实施 Agent 禁止创建子 Agent、派生线程或将部分任务继续委托给其他 Agent。
- 实施 Agent 认为任务需要拆分时，应停止受影响部分并把拆分建议返回协调开发 Agent，不得自行调度。
- 当前实施 Agent 尚未返回最终报告时，协调开发 Agent 不得创建其他实施 Agent处理同一轮任务。

## 实施 Agent 执行顺序

1. 阅读交接材料和适用规范。
2. 检查工作区现状，识别用户或其他 Agent 的已有改动。
3. 将 Spec 验收项映射到具体实现和测试。
4. 在授权范围内进行最小必要改动。
5. 运行与改动相称的测试和静态检查。
6. 自查差异，确认没有无关改动或未说明行为。
7. 按 `.ai/prompts/result-report.md` 返回结果。

同时涉及前端、后端和测试时，实施 Agent 应在同一任务内按可运行的纵向闭环依次完成，不得通过创建子 Agent 并行处理。

## 分层验证

- 实施过程使用直接覆盖当前改动的定向测试；
- 初次实施完成时运行静态检查、单元/集成测试、构建和相关 Browser E2E；
- 默认由后续初次独立验收承担一次完整 Browser E2E，实施 Agent 不机械重复完整矩阵；
- 只有 Spec、任务交接或实际风险升级明确要求时，实施 Agent 才运行完整 Browser E2E；
- 实施报告必须列出验证层级、已运行的定向/相关测试和按策略未运行的完整检查。

## 运行环境

- Node.js 任务开始时只运行一次 `node --version`；当前已经是 Constitution 要求的 Node.js 24 时直接工作，不调用 NVM。
- 只有当前版本不符合要求且必须运行 Node.js 命令时，才允许通过用户现有 NVM 尝试一次 `nvm use`，不得机械执行或重复调用 `nvm list`、`nvm use`。
- NVM 调用失败、无响应或不存在合适版本时，立即停止继续调用并返回协调开发 Agent。
- 未经用户明确授权，不得下载或安装另一套 Node.js，也不得以捆绑运行时、临时安装包或其他版本管理器替代现有 NVM。

## 决策升级

出现以下情况时，实施 Agent 不得自行选择：

- Spec 存在多种会导致不同用户行为的解释；
- 需要扩大范围或修改验收标准；
- 需要新增重要依赖、改变架构或数据语义；
- 需要破坏性迁移、生产操作或额外权限；
- 仓库现状与已确认 Spec 冲突。

实施 Agent 应完成不依赖该决策且不会被推翻的安全工作，然后向协调开发 Agent 返回：

- 决策问题；
- 已知事实和证据；
- 可选方案及影响；
- 当前阻塞范围；
- 建议但不代替用户作出的选择。

## 完成标准

实施完成不等于验收通过。实施 Agent 的完成标准是：

- 授权范围内的实现已完成；
- 测试结果已如实记录；
- 已知限制和风险已列出；
- 没有未披露的需求偏差；
- 工作区改动清单完整；
- 结果已返回协调开发 Agent。

实施 Agent 返回结果后，协调开发 Agent 必须继续保持协调回合活动，处理实施报告，立即删除或释放该实施 Agent，再创建新的独立验收 Agent。平台不支持物理删除时必须停止并永久退役该实施 Agent，禁止通过后续任务复用。实施 Agent 已返回但验收尚未创建或验收结果尚未处理时，整个 Spec 流程仍未完成。

协调开发 Agent 等待实施结果时不得擅自中断仍在运行的 Agent。没有消息、文件改动或工具调用只有在连续超过1小时并经只读检查确认后，才可认定为空转并考虑中断；未达到阈值时只能询问进度并继续等待。用户明确要求停止或出现必须立即制止的高风险越权操作除外。
