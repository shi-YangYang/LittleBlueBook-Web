# 实施工作流

## 进入条件

- 存在用户已确认的 Spec；
- 协调开发 Agent 已完成任务交接；
- 任务范围、验收标准和允许修改的文件范围明确；
- 没有尚未解决且会影响实施结果的关键决策。

## 任务交接

协调开发 Agent 使用 `.ai/prompts/task-handoff.md`，至少提供：

- Spec 路径及确认状态；
- 本轮实施目标；
- 范围内与范围外事项；
- 相关 Constitution、决策、规则和代码上下文；
- 允许修改的目录或文件；
- 必须运行的测试；
- Git 和外部系统授权；
- 结果返回格式。

## 实施 Agent 执行顺序

1. 阅读交接材料和适用规范。
2. 检查工作区现状，识别用户或其他 Agent 的已有改动。
3. 将 Spec 验收项映射到具体实现和测试。
4. 在授权范围内进行最小必要改动。
5. 运行与改动相称的测试和静态检查。
6. 自查差异，确认没有无关改动或未说明行为。
7. 按 `.ai/prompts/result-report.md` 返回结果。

## 决策升级

出现以下情况时，实施 Agent 不得自行选择：

- Spec 存在多种会导致不同用户行为的解释；
- 需要扩大范围或修改验收标准；
- 需要新增重要依赖、改变架构或数据语义；
- 需要破坏性迁移、生产操作或额外权限；
- 仓库现状与已确认 Spec 冲突。

实施 Agent 应完成不依赖该决策且不会被推翻的安全工作，然后向协调开发 Agent 返回：

- 决策问题；
- 已知事实和证据；
- 可选方案及影响；
- 当前阻塞范围；
- 建议但不代替用户作出的选择。

## 完成标准

实施完成不等于验收通过。实施 Agent 的完成标准是：

- 授权范围内的实现已完成；
- 测试结果已如实记录；
- 已知限制和风险已列出；
- 没有未披露的需求偏差；
- 工作区改动清单完整；
- 结果已返回协调开发 Agent。
