# 返工与复验工作流

## 触发条件

验收结论为 `FAIL`，或用户审查后要求修正已实现内容。

用户在 Spec 已经 `Accepted` 后返回的提交或 CI 错误，也触发一次提交后修复循环。该循环由新的实施 Agent 修复、新的验收 Agent 复验，直至错误消除；除非用户明确要求重新打开 Spec，否则不撤销已经确认的 `Accepted` 状态。

## 返工分类

协调开发 Agent 先判断问题属于：

1. **实现偏差**：Spec 清晰，代码未满足要求；
2. **测试或证据缺失**：行为可能正确，但无法按标准验证；
3. **Spec 歧义**：现有文字无法唯一确定正确结果；
4. **需求变化**：用户希望改变原已确认行为；
5. **环境阻塞**：实现或验证依赖不可用。

只有第 1、2 类可以直接进入返工实施。第 3、4 类必须先更新 Spec 并由用户确认。第 5 类先明确解除条件。

## 返工流程

1. 协调开发 Agent 汇总失败项和证据。
2. 如涉及 Spec 变化，先完成重新确认。
3. 创建新的实施 Agent，交接本轮返工范围。
4. 新实施 Agent 修复并返回完整结果。
5. 创建新的验收 Agent 进行复验。
6. 复验覆盖失败项、相关回归项和受改动影响的其他验收项。
7. 重复以上流程，直至 `PASS` 或出现需要用户处理的阻塞。

每轮返工只创建一个实施 Agent，不得把同一轮返工按前端、后端或测试拆给多个并行 Agent；返工 Agent 也不得创建子 Agent。
每个返工或复验 Agent 的报告处理完成后必须立即删除或释放；无法物理删除时立即停止并永久退役。下一轮必须创建新的 Agent，不得复用上一轮实例。

## 返工验证层级

- 小范围返工实施只运行历史失败用例、受影响回归和必要静态检查；
- 小范围独立复验只独立复现历史失败、验证修复和相邻回归；
- 返工和复验默认都不重复初次验收已经完成的完整 Browser E2E；
- 若返工跨越多个模块、修改共享基础设施、引发连锁失败或使既有完整回归失去代表性，协调 Agent 必须在交接中升级验证层级，并说明重新运行完整 Browser E2E 的依据；
- 升级后由返工实施 Agent 在最终工作区状态取得可信的完整通过结果时，新的独立复验 Agent 不再对同一状态重复全套；它只独立复验历史失败项与受影响回归，并明确区分独立证据和复用的完整回归证据；
- 只有返工最终完整结果缺失、失败、不可信，或完整通过后又发生相关变化时，复验阶段才再次运行全套；
- 返工与复验报告必须明确哪些检查按分层策略未运行，不得描述为通过。

## 范围控制

- 返工任务不得借机加入未确认功能。
- 若修复需要扩大范围，必须先由协调开发 Agent 请求用户确认。
- 返工 Agent 不得删除或隐藏原验收证据。
- 每轮报告应标记轮次，并关联上一轮失败项。

## 完成条件

最新验收 Agent 输出 `PASS`，且协调开发 Agent 确认所有历史失败项均有对应修复和复验证据。
