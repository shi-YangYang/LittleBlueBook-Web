# 返工与复验工作流

## 触发条件

验收结论为 `FAIL`，或用户审查后要求修正已实现内容。

## 返工分类

协调开发 Agent 先判断问题属于：

1. **实现偏差**：Spec 清晰，代码未满足要求；
2. **测试或证据缺失**：行为可能正确，但无法按标准验证；
3. **Spec 歧义**：现有文字无法唯一确定正确结果；
4. **需求变化**：用户希望改变原已确认行为；
5. **环境阻塞**：实现或验证依赖不可用。

只有第 1、2 类可以直接进入返工实施。第 3、4 类必须先更新 Spec 并由用户确认。第 5 类先明确解除条件。

## 返工流程

1. 协调开发 Agent 汇总失败项和证据。
2. 如涉及 Spec 变化，先完成重新确认。
3. 创建新的实施 Agent，交接本轮返工范围。
4. 新实施 Agent 修复并返回完整结果。
5. 创建新的验收 Agent 进行复验。
6. 复验覆盖失败项、相关回归项和受改动影响的其他验收项。
7. 重复以上流程，直至 `PASS` 或出现需要用户处理的阻塞。

## 范围控制

- 返工任务不得借机加入未确认功能。
- 若修复需要扩大范围，必须先由协调开发 Agent 请求用户确认。
- 返工 Agent 不得删除或隐藏原验收证据。
- 每轮报告应标记轮次，并关联上一轮失败项。

## 完成条件

最新验收 Agent 输出 `PASS`，且协调开发 Agent 确认所有历史失败项均有对应修复和复验证据。
