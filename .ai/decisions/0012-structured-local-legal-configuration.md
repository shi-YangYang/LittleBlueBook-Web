# 0012：法律公开资料采用未跟踪的结构化本地配置

- 状态：Accepted
- 日期：2026-08-03
- 决策人：用户
- 记录人：协调开发 Agent
- 关联：`specs/spec-012-legal-terms-and-more/spec.md`

## 背景

用户协议、隐私政策和关于页面需要展示运营主体、联系邮箱、适用法律和生效日期。仓库在 GitHub 开源，用户明确不允许把这些真实资料直接写入被 Git 跟踪的 Markdown、TypeScript、环境示例或其他源码文件。

这些资料是结构化、低频变化的法律公开资料，不属于密码或授权码；它们最终会在网站法律页面向访问者展示，但不应因源码开源而直接出现在 Git 历史或客户端 JavaScript 包中。

## 决策问题

如何在保持结构清晰、便于扩展和适配本地/Docker 部署的同时，避免真实法律资料进入 GitHub 源码？

## 备选方案

### 方案 A：运行时环境变量

- 说明：每个字段使用单独环境变量注入；
- 优点：部署工具普遍支持，适合秘密凭据；
- 代价与风险：结构化资料分散，字段增多后维护不直观，用户明确认为不够灵活。

### 方案 B：被 Git 跟踪的 TypeScript 配置

- 说明：把静态资料写入仓库内 TypeScript 文件；
- 优点：类型明确、导入方便；
- 代价与风险：真实值进入 GitHub 和 Git 历史，不满足隐私边界。

### 方案 C：未跟踪的结构化本地 JSON

- 说明：真实值保存在被忽略的 `legal.local.json`，仓库只提交示例 JSON 和服务端加载器；
- 优点：结构清晰、易扩展、与源码隔离，可在 Docker 运行时只读挂载；
- 代价与风险：需要显式校验、缺失处理和部署挂载，不能依赖构建时静态导入。

### 方案 D：未跟踪的 TypeScript 本地文件

- 说明：真实值写在被忽略的 `legal.local.ts`；
- 优点：具备 TypeScript 表达能力；
- 代价与风险：文件缺失会影响 CI/构建模块解析，生产运行时挂载还需要编译或动态加载，部署耦合较高。

## 最终决定

采用方案 C：未跟踪的结构化本地 JSON。

- 本地真实文件为 `frontend/config/legal.local.json`，必须被 Git 忽略；
- 仓库只提交 `frontend/config/legal.example.json` 和不含真实值的服务端 TypeScript 加载器；
- 法律页面在服务端运行时读取并校验 JSON，不把资料加入客户端 JavaScript；
- Docker 镜像不内置真实文件，生产运行时从服务器只读挂载；
- 缺失、非法或仍为占位值时不得静默上线；
- Spec、决策记录、测试和示例只记录字段语义，不记录用户提供的真实值；
- 文档版本号属于公开的应用状态，由后端代码管理，不放在私有 JSON 中。

## 理由

JSON 比环境变量更适合这类可扩展的结构化静态资料，同时避免被跟踪 TypeScript 文件造成源码泄露，也避免未跟踪 TypeScript 对编译和容器运行时的耦合。运行时读取允许同一镜像在不同环境挂载不同资料。

## 影响

- 前端需要服务端专用的模式校验和安全错误处理；
- `.gitignore`、Docker 运行说明和示例配置需要同步；
- 法律页面必须动态服务端渲染；
- 测试只能使用虚构夹具，不得复制真实配置；
- 部署时必须额外挂载服务器本地配置文件；
- 网站访问者仍会在最终法律页面看到运营主体和联系邮箱。

## 后续复审条件

- 需要多运营主体、多品牌、多地区或多语言条款；
- 法律资料需要后台在线编辑、审核和发布；
- 部署平台不支持稳定的只读文件挂载；
- 配置内容转变为高频动态数据；
- 需要专用秘密管理服务统一管理运行时配置。
