## 背景

SPEC-011 首次引入用户间一对一私信。当前项目以 PostgreSQL 作为业务数据真实来源，已配置 Redis，但尚未建立消息队列、Outbox、多实例广播或实时通知基础设施。首期部署目标是单台境外云服务器，但私信需要在两个在线会话间提供接近实时的体验。

## 决策问题

私信应使用纯 HTTP 拉取、单实例 WebSocket 加 PostgreSQL，还是立即引入 Redis Pub/Sub 或消息队列；如何保证断线和推送失败时不丢消息。

## 备选方案

### 方案 A：纯 HTTP 轮询

- 说明：消息持久化后由客户端周期请求最新数据。
- 优点：不增加长连接和新运行时依赖；断线补偿简单。
- 代价与风险：实时性差；空轮询增加数据库和网络压力；已读体验迟缓。

### 方案 B：PostgreSQL 权威持久化加单实例 WebSocket

- 说明：HTTP 负责权威写入，消息先提交 PostgreSQL，再通过单服务器 WebSocket 向在线参与者推送；重连通过 HTTP 游标补齐。
- 优点：实时体验与持久化正确性兼得；推送失败不丢消息；符合当前单服务器阶段。
- 代价与风险：需要长连接、重连、去重、用户绑定和已读竞态处理；不直接支持多服务器广播。

### 方案 C：立即使用 Redis Pub/Sub 或消息队列

- 说明：将消息或推送事件发布到 Redis/队列，由各实例消费并向 WebSocket 客户端广播。
- 优点：支持多实例和后续跨服务扩展。
- 代价与风险：需要事件可靠性、重试、幂等、顺序、死信、监控和 PostgreSQL 双写设计；当前规模无需支付该复杂度。

## 最终决定

选择方案 B：

- PostgreSQL 是会话、消息、未读和已读边界的唯一真实来源；
- 会话在首条消息成功持久化时于同一事务创建；
- HTTP 是权威消息发送通道；
- 消息只在 PostgreSQL 提交成功后通过 WebSocket 推送；
- WebSocket 推送失败不回滚持久化消息；
- 客户端重连、页面恢复和窗口重新获得焦点时使用 HTTP 游标同步遗漏消息；
- 消息使用客户端请求 ID 和数据库唯一约束去重；
- WebSocket 使用现有会话 Cookie、Origin 和用户绑定校验；
- 本期不使用 Redis 保存私信、未读、已读或作为 WebSocket 跨实例适配器；
- 当前只承诺单服务器实例内的实时推送，但持久化同步在任何时候可用。

## 理由

当前产品需要的是可靠的一对一实时体验，不是分布式消息平台。先持久化再推送把消息可靠性与 WebSocket 可用性解耦；HTTP 游标补偿使任意断线都不会成为消息丢失。同时，不提前引入 Redis 双写和多实例协调复杂度。

## 影响

- 数据库需要会话、消息、幂等请求 ID 和已读边界；
- 后端需要 HTTP 私信模块和 WebSocket 网关；
- 前端需要连接状态、去重、重连、焦点同步和已读前进；
- 验收需要两个独立浏览器上下文和真实断线补偿证据；
- 单机部署需要正确转发 WebSocket Upgrade；
- 未来多实例部署前不能假设当前内存连接映射可跨实例工作。

## 后续复审条件

出现以下任一情况时重新评估：

- 生产环境需要同时运行多个后端实例；
- 单实例长连接数、消息吞吐或重连风暴超出可验证边界；
- 已确认需要跨服务消息、移动推送、离线任务或可靠事件投递；
- 项目已建立 Outbox、消费者幂等、重试、死信、监控和灾难恢复能力；
- 产品需要在线状态、正在输入、群聊或更高级实时协作。
