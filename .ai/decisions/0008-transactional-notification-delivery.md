# 0008：PostgreSQL 事务性通知交付基线

## 背景

SPEC-009 将首次把点赞、收藏、评论和关注转化为接收者可查看的通知。工程基础已经包含 PostgreSQL 和 Redis，但当前没有实时通知、跨服务事件总线或大规模投递指标。通知需要与互动状态保持一致，同时支持历史列表、未读状态和权限隔离。

## 决策问题

首期通知应采用 PostgreSQL 同步事务写入、异步消息投递，还是在读取时从现有互动表临时推导；是否需要 Redis 或 WebSocket。

## 备选方案

### 方案 A：PostgreSQL 事务性通知表

- 说明：互动状态从未建立变为建立或评论创建时，在同一 PostgreSQL 事务内写入持久化通知；列表和未读状态直接查询 PostgreSQL。
- 优点：互动与通知原子一致；历史、已读、权限和分页语义清晰；无需新增投递服务和双写链路。
- 代价与风险：互动写路径增加一次数据库写入；通知规模增长后可能需要归档和读优化。

### 方案 B：消息队列异步投递

- 说明：互动成功后发布事件，由消费者异步创建通知，并可通过 WebSocket 推送。
- 优点：更适合高吞吐、跨服务扩展和实时交付。
- 代价与风险：需要 Outbox、消息队列、消费者幂等、重试、死信、监控和最终一致性处理；当前没有需求证明复杂度必要。

### 方案 C：从互动表动态推导

- 说明：不建立通知表，每次打开通知页时联合查询点赞、收藏、评论和关注。
- 优点：少一张持久化表。
- 代价与风险：无法可靠表达已读、历史保留和取消后仍保留通知；多来源分页、权限和性能复杂。

## 最终决定

选择方案 A：

- PostgreSQL 是首期通知及未读状态的唯一真实来源；
- 互动写入与通知创建在同一个数据库事务中完成；
- 只有真实业务状态变化生成通知，重复幂等请求不生成；
- 取消互动不删除通知，取消后重新建立可以产生新通知；
- 不回填 SPEC-009 启用前已经存在的历史互动通知；
- 通知使用稳定游标分页和数据库索引；
- 本期不使用 Redis 保存通知、未读数或投递事件；
- 本期不引入消息队列、Outbox、WebSocket、SSE 或轮询实时推送；
- 用户通过进入页面、刷新或重新导航拉取最新通知。

## 理由

当前阶段的核心目标是建立准确、可验收的通知闭环，而不是实时分布式投递。PostgreSQL 事务可以直接保证互动和通知共同成功或失败，避免异步投递缺失、重复消费和缓存双写问题，也能自然支持历史、已读和权限查询。

## 影响

- 数据库新增通知模型、类型、外键和分页/未读索引；
- 点赞、收藏、评论和关注写流程需要纳入事务性通知创建；
- 通知读取和已读更新直接访问 PostgreSQL；
- 取消互动仍保留历史通知，通知表不能依赖互动关系持续存在；
- 评论和笔记删除需要采用 `SET NULL` 或等价保留策略；
- 前端不承诺实时更新，需明确拉取时机；
- Redis 继续作为工程基础依赖，但 SPEC-009 不增加通知相关键或消费者。

## 后续复审条件

出现以下任一情况时重新评估：

- 生产指标证明通知写入显著拖慢互动事务；
- 通知查询、未读统计或存储增长持续超过已确认预算；
- 产品确认需要秒级实时通知、推送渠道或跨服务事件；
- 系统拆分为多个独立服务，无法继续使用单数据库事务；
- 项目已经具备 Outbox、消息队列、消费者幂等、重试、监控和故障恢复能力；
- 已确认需要通知归档、过期或冷热分层。
