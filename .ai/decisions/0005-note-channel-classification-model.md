# 0005：笔记频道分类模型

- 状态：Accepted
- 日期：2026-07-27
- 决策人：用户
- 记录人：协调开发 Agent
- 关联：`specs/spec-006-note-channels/`

## 背景

首页已经展示一组频道导航，但当前只有“推荐”会加载真实笔记，其他频道仍是前端占位按钮。笔记数据也没有频道字段，发布时无法分类。SPEC-006 需要打通“发布选择频道 → 持久化 → 首页频道筛选 → 详情展示”的完整闭环。

频道列表会随着产品发展发生增删、排序和停用。将频道写成数据库枚举会使每次调整都依赖 Schema 迁移，也无法自然表达显示顺序、启用状态和内部迁移频道。

## 决策问题

确定频道的持久化模型、“推荐”的语义、新旧笔记分类方式，以及频道配置和笔记之间的约束。

## 备选方案

### 方案 A：代码或数据库枚举

- 说明：在前后端代码或 Prisma Enum 中固定所有频道；
- 优点：实现简单，类型约束直接；
- 代价与风险：新增、排序、停用频道需要修改代码或数据库结构，难以承载内部频道。

### 方案 B：数据库频道表

- 说明：使用频道表保存稳定代码、中文名称、顺序、启用和可发布状态，笔记通过外键关联；
- 优点：频道身份稳定，支持后续调整和管理能力，能够安全处理历史未分类笔记；
- 代价与风险：需要种子数据、公开列表接口和更多完整性约束。

## 最终决定

采用方案 B：

- 每篇新笔记必须且只能关联一个可发布频道；
- “推荐”是聚合信息流，不是频道记录，也不能由发布者选择；
- 公开可发布频道依次为：数码、汽车、游戏、运动、健身、户外、穿搭、美食、职场、情感、家居、旅行、其它；
- “视频”不属于本期频道，待视频发布能力形成独立 Spec 后再决定是否恢复；
- 频道表至少保存稳定英文代码、中文名称、显示顺序、启用状态和可发布状态；
- 已有笔记迁移到内部“未分类”频道；该频道不出现在导航和发布选择中；
- “推荐”展示所有公开笔记，包括历史未分类笔记；
- 具体频道只展示属于该频道的笔记；
- 频道停用只阻止新的发布和频道入口访问，不自动删除、迁移或隐藏既有笔记；
- 本期不提供频道管理后台。

## 理由

- 频道表能够在不改变笔记数据结构的情况下扩展后续频道管理；
- 稳定代码可以用于 URL 和 API，不把中文文案作为数据库或路由身份；
- 内部未分类频道避免擅自给历史内容分配业务分类；
- 推荐作为虚拟聚合入口，可以继续承担全站最新公开内容信息流。

## 影响

- 数据库新增频道表和笔记频道外键；
- 迁移需要幂等创建系统频道，并为所有既有笔记回填内部未分类频道；
- 发布接口新增必填频道代码；
- 首页需要读取公开频道列表并按频道筛选；
- 笔记详情需要返回并展示可公开的频道信息；
- 频道删除策略为受外键约束的保留或停用，不允许直接导致笔记丢失。

## 后续复审条件

当项目需要频道管理后台、多频道笔记、用户自定义频道、频道关注、频道级审核、视频内容分类或推荐算法时重新评估。
