# 0004：分层本地验证策略

- 状态：Accepted
- 日期：2026-07-27
- 决策人：用户
- 记录人：协调开发 Agent
- 关联：`AGENTS.md`、`constitution/tech-stack.md`、`.ai/rules/testing.md`、`.ai/workflows/`

## 背景

此前每轮实施、独立验收、返工和复验都会分别运行静态检查、单元测试、构建及完整三浏览器 E2E。一次存在返工的 Spec 可能重复执行四次完整 E2E 和多次完整构建，虽然保证了独立性，但大量检查覆盖范围相同，导致交付时间过长。

实施与验收的独立性来自 Agent 身份、差异审查、独立判断和关键证据，而不是要求每一个阶段机械重复完全相同的全量命令。

## 决策问题

如何在保留 SDD、多 Agent 独立验收和必要回归保障的同时，减少实施、验收、返工和复验之间的重复测试。

## 备选方案

### 方案 A：每阶段完整回归

- 说明：实施、验收、返工、复验均运行完整静态检查、构建和三浏览器 E2E；
- 优点：每个阶段都有完整命令结果；
- 代价与风险：高度重复，反馈慢，小范围修复也承担与大型功能相同的时间成本。

### 方案 B：按阶段和风险分层验证

- 说明：开发阶段使用定向反馈，初次独立验收承担一次完整回归，小范围返工与复验只覆盖失败项和受影响回归；
- 优点：保留独立验收和风险覆盖，显著减少重复构建及 Browser E2E；
- 代价与风险：需要在交接中明确验证层级，并由 Agent 判断改动是否扩大到必须重新全量回归。

## 最终决定

采用方案 B：

1. 实施过程中只运行直接覆盖当前改动的定向测试；
2. 初次实施完成时运行静态检查、单元/集成测试、构建和与当前 Spec 直接相关的 Browser E2E，不机械运行完整 Browser E2E；
3. 初次独立验收运行一次完整 Browser E2E，作为该轮 Spec 的完整浏览器回归，并独立检查关键验收项；
4. 小范围返工实施只运行失败用例、受影响回归和必要的静态检查；
5. 小范围返工后的独立复验只独立验证历史失败项和受影响回归，不机械重跑完整 Browser E2E；
6. 只有修改范围较大、涉及共享基础设施、发现连锁风险、前一次完整回归已失去代表性，或验收 Agent 有证据认为影响无法界定时，才再次运行完整 Browser E2E；
7. Chromium 作为普通浏览器业务回归的主要执行环境；Firefox 和 WebKit 只覆盖布局、滚动、历史导航、文件上传、媒体、弹框、焦点、Cookie 等存在浏览器差异风险的关键场景；
8. 未运行的检查必须在报告中说明分层依据，不能把“按策略未运行”写成“已通过”；
9. CI 范围不变，常规 CI 仍不运行 Browser E2E。

## 理由

- 将完整 Browser E2E 集中在初次独立验收，可以同时满足完整回归和验收独立性；
- 实施阶段的定向 Browser E2E 能更快发现和修复当前功能问题；
- 小范围返工的风险边界已经由失败证据限定，重复全部三浏览器矩阵通常不会增加等比例的有效证据；
- 明确升级条件可以防止为了速度而漏掉真实的跨模块回归。

## 影响

- 协调 Agent 的任务交接必须写明本轮验证层级、必跑项和是否需要完整 Browser E2E；
- 实施和返工报告必须区分定向验证、相关回归和完整回归；
- 验收 Agent仍须独立审查差异和运行关键检查，不得直接采信实施报告；
- Spec 可以基于自身风险增加更严格的测试要求，但不得无理由机械复制全量测试到每个阶段；
- 已经完成的历史测试记录保持不变。

## 后续复审条件

当项目建立发布前 Browser E2E 门禁、测试套件可以可靠按改动范围自动选择、出现因分层策略漏检的严重回归，或完整 E2E 执行时间和稳定性发生重大变化时重新评估。
