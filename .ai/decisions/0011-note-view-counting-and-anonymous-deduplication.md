# 0011：笔记有效浏览量与匿名去重基线

## 背景

SPEC-011 要求笔记展示真实浏览量。笔记详情是公开页面，需要同时处理登录用户和匿名浏览，但项目不应为了浏览量建立 IP 追踪、设备指纹或无限增长的完整行为流水。浏览量也必须在并发刷新下保持一致。

## 决策问题

笔记浏览量是计每次请求、每日独立用户，还是有时间窗口的有效访问；匿名用户如何去重且不建立过度追踪。

## 备选方案

### 方案 A：每次详情请求都计数

- 说明：每次读取详情接口都对总数加一。
- 优点：实现最简单，不需要访客标识。
- 代价与风险：预取、重试、刷新、作者自访问和机器请求会显著虚增；读接口产生难以控制的写副作用。

### 方案 B：`30` 分钟窗口的有效访问

- 说明：只在详情成功展示后单独上报；登录用户使用用户 ID，匿名访客使用随机 Cookie 的不可逆哈希，同一主体与笔记在 `30` 分钟内只计一次；作者自访问不计。
- 优点：保留重复访问的产品含义，同时降低刷新和预取虚增；不需要 IP 或设备指纹；只保存最后有效时间。
- 代价与风险：Cookie 被清除后会视为新访客；不是反欺诈或分析级独立访客。

### 方案 C：基于 IP/设备指纹的每日 UV

- 说明：组合 IP、User-Agent 或更多设备信号识别每日唯一访客。
- 优点：更接近分析意义的每日 UV。
- 代价与风险：隐私和合规成本更高；共享网络、代理、VPN 和浏览器反指纹会导致假合并或假拆分；超出当前产品目标。

## 最终决定

选择方案 B：

- 浏览量定义为详情页成功展示后上报的有效访问；
- 列表卡片曝光不计数；
- 笔记作者自访问不计数；
- 同一登录用户与笔记在 `30` 分钟内只计一次；
- 同一匿名访客 Cookie 与笔记在 `30` 分钟内只计一次；
- 匿名 Cookie 为服务端高熵随机值，使用 `HttpOnly`、`SameSite=Lax` 和环境相符的 `Secure`；
- 数据库只保存带服务端秘密的不可逆哈希或等价不可还原标识；
- 不保存 IP、User-Agent、设备指纹或原始 Cookie；
- 每个笔记与去重主体组合只保存最后有效浏览时间，不保存完整流水；
- 去重判断、最后时间更新和笔记权威总数增加在同一 PostgreSQL 事务或等价原子语义内完成；
- 本期不使用 Redis 计数或去重。

## 理由

`30` 分钟窗口能在“每次打开都有价值”与“连续刷新不应立即虚增”之间取得平衡。随机 Cookie 与不可逆哈希提供了足够的本地去重能力，避免收集 IP 和设备指纹。只保存最后有效时间，也避免为首期浏览数建立无限增长的行为事件表。

## 影响

- 笔记模型需要权威浏览总数；
- 需要笔记与去重主体的唯一关系和最后有效时间；
- 详情页需要在成功展示后单独上报，不应让 GET 详情隐式写入；
- 匿名访客 Cookie 变成需要稳定密钥与正确部署属性的运行配置；
- 验收需要登录、匿名、作者、超时窗口和并发探针；
- 该指标不可对外宣称为严格 UV 或反欺诈统计。

## 后续复审条件

出现以下任一情况时重新评估：

- 产品需要独立访客、日/月活跃、漏斗或完整浏览事件分析；
- 匿名去重表增长、清理或查询成本超出可接受边界；
- 业务需要反刷量、风控或统计审计；
- 数据合规要求改变 Cookie 同意、保留期限或匿名标识策略；
- 生产指标证明 PostgreSQL 原子更新成为热点，需要重新评估聚合、分区或缓存。
