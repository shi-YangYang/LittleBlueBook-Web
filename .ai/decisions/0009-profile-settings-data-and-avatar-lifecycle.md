# 0009：个人资料数据、隐私与头像生命周期

## 背景

用户资料目前只有昵称、不可变小蓝书号、性别和昵称首字默认头像。SPEC-010 需要加入出生日期、年龄公开、简介和自定义头像，同时影响个人主页、历史笔记、评论、通知和搜索。项目当前使用 PostgreSQL 和本地 MediaStorage，尚未引入 CDN 或外部对象存储。

## 决策问题

年龄应保存为数字还是从出生日期计算；头像应原样存储还是标准化；资料保存、缓存、多窗口冲突和旧头像清理如何保证一致。

## 备选方案

### 方案 A：出生日期 + 隐私开关 + 标准化头像 + 版本化整体保存

- 说明：保存出生日期并实时计算年龄；公开由开关控制；头像服务端统一生成 `512×512 WebP`；全部字段使用版本条件整体保存；文件变更采用暂存和补偿。
- 优点：年龄不会过期；隐私边界明确；头像格式、缓存和显示稳定；避免部分更新及多窗口静默覆盖。
- 代价与风险：需要图像处理、文件补偿、统一头像传播和更多异常测试。

### 方案 B：直接保存年龄并原样上传头像

- 说明：用户填写整数年龄，头像文件按原格式保存。
- 优点：实现较少。
- 代价与风险：年龄每年失真；原图带元数据和格式差异；缓存和安全边界弱；难以保证统一显示。

### 方案 C：使用第三方头像和资料服务

- 说明：把头像处理、存储或资料托管交给外部服务。
- 优点：部分媒体能力可以外包。
- 代价与风险：新增成本、外部依赖、隐私传输、供应商绑定和部署配置；当前没有必要。

## 最终决定

选择方案 A：

- 数据库保存出生日期，不保存年龄数字；
- `showAge` 默认 `false`，公开接口只返回计算后的年龄；
- 完整出生日期和邮箱只在本人设置接口返回；
- 昵称、性别、出生日期、公开年龄、简介和头像作为一次整体保存；
- 使用不透明资料版本阻止多窗口静默覆盖；
- 头像输入限 JPEG/PNG/WebP、`5 MiB`、裁剪区域至少 `512×512`；
- 服务端统一生成 `512×512 WebP`，移除元数据并处理透明背景；
- 头像继续使用既有 MediaStorage 和本地持久化目录；
- 每次新头像使用新的不可预测对象 Key；
- 新文件暂存、失败补偿、旧文件清理必须可追踪，不允许无记录的孤立文件；
- 最新头像和昵称通过实时关系查询传播到既有笔记、评论、通知和搜索，不保存公开资料快照；
- 不引入 Redis、CDN、第三方头像服务或新对象存储。

## 理由

出生日期是稳定事实，年龄是随日期变化的派生值；隐私开关可以避免公开完整生日。统一 WebP头像减少跨页面格式差异，重新编码可以移除不必要元数据。版本条件和整体保存使用户能明确理解一次操作的结果，暂存与补偿则控制文件系统和数据库之间的一致性风险。

## 影响

- 用户表需要新增生日、公开年龄、简介和头像引用；
- 可能需要头像待清理记录或等价可追踪机制；
- Profile API 需要私有设置读取和版本化保存；
- 媒体模块需要头像专用验证与标准化；
- notes、interactions、notifications、search 和页面外壳需要统一头像映射；
- 公开 DTO 必须保持邮箱和完整生日白名单边界；
- 部署继续要求媒体持久化目录挂载；
- 测试需要覆盖存储失败、数据库失败、版本冲突和多页面传播。

## 后续复审条件

出现以下任一情况时重新评估：

- 生产头像量或带宽使单机媒体服务成为持续瓶颈；
- 项目迁移至 S3 兼容对象存储或 CDN；
- 产品需要头像审核、历史版本、资料可见范围或修改频率限制；
- 文件清理重试量需要独立后台任务或消息队列；
- 多服务架构无法继续使用当前资料保存和补偿边界；
- 监管或产品年龄策略发生变化。
