# 0001：CI/CD 与初期生产部署基线

- 状态：Accepted
- 日期：2026-07-24
- 决策人：用户
- 记录人：协调开发 Agent
- 关联：`constitution/tech-stack.md`

## 背景

LittleBlueBook-Web 后续需要持续集成和持续交付。初期生产环境是一台租用的境外云服务器，需要在控制成本和运维复杂度的同时，保证构建结果可重复、发布经过人工确认并且可以追踪版本。

## 决策问题

确定代码托管、CI/CD 平台、镜像仓库、生产容器管理方式和生产发布门禁。

## 备选方案

### GitHub 托管的一体化流程

- GitHub 托管代码；
- GitHub Actions 执行 CI/CD；
- GHCR 保存容器镜像；
- Docker Compose 管理单服务器生产容器；
- 通过 `workflow_dispatch` 人工触发生产部署。

优点是代码、流水线和镜像权限可以集中管理，适合境外服务器和当前单机部署规模。

### 在生产服务器拉取源码并现场构建

部署步骤较少，但生产服务器需要安装完整构建环境，构建结果更难复现，也容易将未经验证的环境差异带入生产。

### Kubernetes 或其他多节点编排

提供更强的调度和滚动发布能力，但明显超出初期单服务器需求，并增加运维复杂度。

## 最终决定

- 代码托管使用 GitHub；
- CI/CD 使用 GitHub Actions；
- 镜像仓库使用 GitHub Container Registry（GHCR）；
- 前端和后端分别构建 Docker 镜像；
- 初期生产环境为一台境外云服务器；
- 生产容器使用 Docker Compose 管理；
- 生产发布由 `workflow_dispatch` 人工触发；
- 日常开发提交只执行 CI，不要求逐个发布正式生产镜像；
- 正式发布以选定 `main` 提交上的 `vMAJOR.MINOR.PATCH` Git Tag 触发；
- 正式镜像同时使用发布版本和 Git Commit SHA 进行不可变追踪，不以 `latest` 作为唯一版本；
- CI、正式镜像发布和生产部署分别由 `ci.yml`、`release-images.yml` 和 `deploy-production.yml` 承担；
- 本地 Docker 构建只用于验证，不作为正式发布产物；
- 生产服务器拉取已通过 CI 的镜像，不负责应用源码构建；
- 当前不引入 Kubernetes。

## 理由

- 与现有 GitHub 仓库自然集成；
- CI 生成的镜像可以作为唯一部署产物；
- 开发提交与正式发布版本分离，可以在多轮本地开发后只发布选定版本；
- 人工发布门禁适合初期单生产环境；
- Docker Compose 足以管理单服务器服务；
- 为未来回滚、审计和自动化发布保留清晰版本边界。

## 影响

- 仓库后续需要建立 CI、镜像构建和人工部署工作流；
- 创建正式版本标签前，需要确认对应提交位于 `main` 且已经通过强制 CI；
- 云服务器需要安装 Docker Engine 和 Docker Compose；
- 云服务器需要安全地获取私有镜像，并使用受限部署凭据；
- 生产配置和密钥不得写入镜像或提交到仓库；
- 媒体文件和数据库等有状态数据必须独立持久化和备份；
- 数据库迁移、健康检查、服务器初始化和回滚细节需要在部署实施前进一步确认。

## 后续复审条件

出现多服务器部署、可用性目标显著提高、境内部署、镜像仓库访问不稳定或需要无人值守自动发布时重新评估。
