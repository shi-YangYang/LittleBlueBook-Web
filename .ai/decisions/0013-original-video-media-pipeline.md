## 背景

SPEC-013 首次引入视频发布和播放。项目当前使用单机本地持久化媒体，尚未购买对象存储/CDN，也没有转码服务。视频文件比图片大得多，如果沿用内存 multipart 会显著增加 Node.js 堆风险；如果没有 Range，播放器拖动会重复下载完整文件；如果引入 FFmpeg、转码队列或 S3 分片，又会扩大本地开发和部署复杂度。

## 决策问题

首期视频应采用原始文件直出、服务端转码，还是直接建设对象存储分片上传；如何同时满足格式验证、资源上限、播放拖动和未来迁移边界。

## 备选方案

### 方案 A：本地流式接收原始 MP4并支持 Range

- 说明：只接受 H.264 MP4，音频存在时为 AAC；服务端用 Node.js 内部解析元数据，流式写入私有临时区，验证后原子归属；播放使用原始文件和 HTTP Range；封面由浏览器提取或用户上传。
- 优点：符合当前单机部署和存储抽象；不要求额外系统运行时；内存有界；能够完成基础播放、进度拖动和未来 S3 迁移。
- 代价与风险：不转码，兼容输入范围较窄；没有多清晰度，弱网与带宽体验有限；浏览器封面提取可能失败。

### 方案 B：本地 FFmpeg 验证并转码

- 说明：后端依赖 FFmpeg/ffprobe，把输入统一转为 H.264/AAC，并可生成封面或多清晰度文件。
- 优点：输入兼容范围更广，服务端输出统一，后续可扩展 HLS。
- 代价与风险：本机和容器增加大型系统依赖、CPU/磁盘峰值、超时、队列和任务恢复问题；同步请求不适合长时间转码；超出首期目标。

### 方案 C：S3 兼容对象存储分片直传与云端处理

- 说明：客户端取得签名后分片上传对象存储，由异步任务转码并通过 CDN 分发。
- 优点：适合大文件、断点续传、多机扩展和生产分发。
- 代价与风险：现在没有对象存储/CDN预算与运行环境；需要签名、回调、异步状态、费用和供应商配置；显著扩大范围。

## 最终决定

选择方案 A，并确定：

- 一条视频笔记只包含一个视频；
- 输入只接受 MP4，视频轨道为 H.264，音频可无，存在时为 AAC；
- 时长为 `1 秒～10 分钟`，文件最大 `100 MiB`；
- 不安装或依赖 FFmpeg/ffprobe，不进行转码或多清晰度处理；
- 服务端以 Node.js 内部媒体解析独立验证容器、编码、时长、宽高和大小；
- 视频以有界内存流式写入私有临时区，验证和数据库归属完成前不可公开；
- 同一账号同时一个上传，滚动 60 分钟最多 10 次；Redis 只保存限流和短期占用；
- 取消、失败和异常均补偿清理；停止写入超过一小时的未归属临时文件由启动检查和定时任务清理；
- 自定义封面优先；未提供时由浏览器提取首个可解码画面，失败则要求手动封面；
- 视频公开读取支持完整 GET、HEAD 和 HTTP 单 Range `206`，区间读取不得缓冲完整文件；
- 媒体仍通过可替换存储接口访问，数据库只保存随机对象 Key 和元数据；
- Docker 部署必须挂载持久化媒体目录；
- 常规 CI 不安装浏览器、不运行视频 Browser E2E。

## 理由

该方案在当前单机、无对象存储和无转码基础设施的现实条件下，提供了安全可控的首期视频闭环。限定 H.264/AAC 能够让原始文件直接面向主流浏览器；流式写入和 Range 解决大文件的核心内存与拖动问题；统一存储抽象避免把业务代码锁定在本地磁盘，为未来迁移保留路径。

## 影响

- 现有图片用的内存 multipart 不能直接复制到视频路径；
- 后端需要受门禁保护的流式上传、临时目录、清理任务和 MP4 元数据解析；
- 媒体存储接口需要元数据、流式写入和区间读取能力；
- 前端需要真实上传进度、取消、封面提取和失败降级；
- 播放质量与带宽完全取决于原始文件；
- 生产磁盘容量、备份和出口流量需要监控；
- 浏览器差异验收必须覆盖 Chromium、Firefox 和 WebKit 的关键媒体行为。

## 后续复审条件

出现以下任一情况时重新评估：

- 用户需要上传非 H.264/AAC 视频或需要服务端统一压缩；
- 需要多清晰度、HLS/DASH、缩略图队列、字幕或审核处理；
- 需要超过 100 MiB、断点续传或弱网续传；
- 单机磁盘、备份、出口带宽或并发成为瓶颈；
- 部署扩展为多实例，无法继续依赖单机共享目录；
- 决定采购 S3 兼容对象存储、CDN 或媒体处理服务；
- Node.js 内部解析无法可靠覆盖生产输入，需要引入隔离的媒体处理服务。
