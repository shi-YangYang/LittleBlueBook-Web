## 背景

SPEC-007 将首次引入笔记点赞、收藏、评论和用户关注。工程基础已经包含 PostgreSQL 和 Redis，但“基础依赖存在”不等于每项业务都应立即使用缓存。互动关系涉及唯一性、权限、取消操作、精确统计和跨页面一致性，必须先明确权威数据源和缓存边界。

## 决策问题

首期社交互动是否直接引入 Redis 缓存或以 Redis 承担互动计数，以及如何保证互动关系和数量一致。

## 备选方案

### 方案 A：PostgreSQL 作为唯一真实来源，本期不使用 Redis

- 说明：点赞、收藏、评论和关注使用规范化关系表、唯一约束、外键、索引和事务；读取直接查询 PostgreSQL。
- 优点：数据语义清晰，取消、并发和权限行为易于验证；没有缓存失效与双写一致性问题。
- 代价与风险：用户量增长后，高频计数和热门内容读取可能增加数据库负载，需要基于真实指标再优化。

### 方案 B：首期同时引入 Redis 互动缓存

- 说明：关系仍持久化到 PostgreSQL，同时把计数或状态缓存到 Redis。
- 优点：在极高读取量下可以降低部分数据库查询压力。
- 代价与风险：立即引入缓存键设计、失效、回填、双写失败、计数漂移和故障降级问题；当前没有性能数据证明这些复杂度必要。

### 方案 C：Redis 作为互动主存储

- 说明：互动关系或计数优先写入 Redis，再异步落库。
- 优点：可以追求较低写入延迟和高吞吐。
- 代价与风险：显著增加数据丢失、重复消费、最终一致性、恢复和运维复杂度，不适合当前阶段。

## 最终决定

选择方案 A：

- PostgreSQL 是点赞、收藏、评论和关注的唯一真实来源；
- 使用数据库唯一约束防止重复点赞、收藏和关注；
- 使用外键、索引、事务和幂等目标状态接口保证完整性与并发一致性；
- 互动数量从真实有效关系计算，或使用由同一数据库事务严格保证的等价方案；
- SPEC-007 不读取或写入 Redis 互动缓存；
- 不因 Redis 已经存在于工程基础而机械使用 Redis。

## 理由

当前项目处于功能闭环建设阶段，没有互动流量、数据库负载或响应时间数据证明 PostgreSQL 已成为瓶颈。先保持单一权威数据源可以降低错误计数、缓存失效和双写失败风险，也更有利于独立验收验证真实业务结果。

## 影响

- 数据库需要新增点赞、收藏、评论和关注模型及相应索引；
- 互动写接口需要幂等语义和数据库约束；
- 查询实现需要避免无界 N+1，并通过真实测试观察性能；
- Redis 继续保留为项目基础依赖，但 SPEC-007 不为互动功能增加缓存键、消费者或同步任务；
- 后续缓存必须作为明确的性能优化决策，而不是当前 Spec 的隐含要求。

## 后续复审条件

出现以下任一情况时重新评估：

- 生产监控证明互动计数或列表查询成为主要数据库瓶颈；
- PostgreSQL CPU、连接数、I/O 或查询延迟持续超过已确认的性能预算；
- 热门笔记产生明显读热点，索引和查询优化仍不足；
- 产品引入实时排行榜、热点推荐或大规模互动事件流；
- 项目建立了缓存一致性、降级、回填和监控能力。
