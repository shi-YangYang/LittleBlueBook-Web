## 背景

SPEC-008 将首次建立笔记和用户搜索。项目已有 PostgreSQL 18 和 Prisma 7，但尚未确认搜索能力。首期搜索需要支持中文子串、英文大小写不敏感、多字段匹配、排序和分页，同时当前没有生产数据证明必须维护独立搜索集群。

## 决策问题

首期搜索应直接使用 PostgreSQL、使用无索引包含扫描，还是引入 Elasticsearch、OpenSearch、Meilisearch 等独立搜索服务。

## 备选方案

### 方案 A：PostgreSQL `pg_trgm` 与 GIN 索引

- 说明：PostgreSQL 保持唯一真实来源，通过 `pg_trgm` 和 GIN 索引支持 `LIKE/ILIKE` 包含搜索。
- 优点：无需新增服务和数据同步链路；支持当前中文子串和英文搜索需求；迁移、测试和运维边界较小。
- 代价与风险：复杂相关性、海量数据、分词、同义词和搜索分析能力有限；需要数据库扩展权限和查询计划验证。

### 方案 B：PostgreSQL 无扩展的 `ILIKE`

- 说明：直接执行包含匹配，不建立 trigram 索引。
- 优点：实现最简单，没有扩展依赖。
- 代价与风险：数据增长后容易形成全表扫描；不适合作为大型 Web 系统的长期首期基线。

### 方案 C：独立搜索服务

- 说明：把笔记和用户索引同步到 Elasticsearch、OpenSearch 或 Meilisearch。
- 优点：更强的相关性、分词、扩展和搜索分析能力。
- 代价与风险：立即引入索引同步、最终一致性、回填、故障恢复、监控和额外部署成本；当前没有数据证明复杂度必要。

## 最终决定

选择方案 A：

- PostgreSQL 是首期搜索唯一真实来源；
- 启用可信扩展 `pg_trgm`；
- 为笔记标题、正文和用户昵称建立必要的 GIN trigram 索引；
- 使用参数化 `LIKE/ILIKE` 或等价 trigram 查询实现包含搜索；
- 小蓝书号使用现有唯一索引和必要的补充查询优化；
- 不使用 Redis 搜索缓存；
- 不引入独立搜索服务、消息队列或异步索引任务。

## 理由

该方案可以在现有基础设施内满足已确认的搜索范围，同时避免无索引全表扫描和独立搜索系统的数据一致性成本。PostgreSQL 官方文档明确说明 `pg_trgm` 的 GiST/GIN 操作类支持 `LIKE` 和 `ILIKE` 索引搜索，符合本期包含匹配需求。

## 影响

- 数据库迁移需要幂等启用 `pg_trgm`；
- 开发、测试、CI 和生产 PostgreSQL 必须允许安装可信扩展；
- 搜索查询需要验证代表性执行计划和稳定游标；
- Prisma 无法直接表达的扩展和索引使用版本化 SQL 迁移承载；
- 搜索数据不需要复制到 Redis 或其他服务；
- 未来若切换独立搜索服务，PostgreSQL 仍保留权威业务数据。

## 后续复审条件

出现以下任一情况时重新评估：

- 生产数据量或查询并发使 PostgreSQL 搜索成为持续瓶颈；
- 已确认需要中文分词、同义词、拼音、纠错或复杂相关性；
- 查询计划和索引优化后仍无法达到已确认性能预算；
- 需要跨多种实体的大规模统一搜索；
- 项目已经具备独立搜索服务的同步、回填、监控、降级和故障恢复能力。
