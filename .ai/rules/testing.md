# 测试与验证规则

## 原则

- 每项验收标准都应有可执行或可观察的验证方式。
- 测试强度应与改动风险相称。
- 实施 Agent 的自测不能替代独立验收。
- 所有报告必须区分“通过”“失败”“未运行”和“无法运行”。

## 最小充分验证与执行效率

- 验证目标是用最小、可靠的证据证明当前改动，而不是让每个任务都执行相同的全量命令。
- “连续空转超过1小时才可考虑中断子 Agent”只限制协调 Agent 的终止行为，不构成任何任务的最低运行时长。
- 普通文档、Spec 状态、验收记录、提交信息或其他不改变运行时代码的任务，默认只做内容一致性、格式和 `git diff --check`；不运行 Node.js 版本检查、Docker、Lint、类型检查、单元测试、构建或 Browser E2E。
- 小型 Bug 和局部代码修改的默认验证集合为：修复前可复现证据、修复后的最小定向测试、直接受影响回归，以及仅对改动文件适用的静态检查。
- 小型任务不得仅因为仓库存在全量脚本，就机械运行全仓格式、Lint、类型、测试、构建和 Browser E2E。
- 同一工作区状态下，同一角色和同一阶段已经通过的命令不得无理由重复运行；代码、配置、依赖或测试数据发生相关变化时才重新运行。
- 协调开发 Agent 应读取实施和验收报告、检查差异并推进流程，不得在 Agent 已提供可信证据后再重复执行同一套测试。独立验收必须保持独立，但只需按本文件规定的验收层级运行一次相应检查。
- 优先复用健康的 Docker 容器、已安装的 `node_modules`、浏览器和可用本地服务；只有环境缺失、状态污染或隔离要求有证据时才重新创建。
- 普通文档任务以数分钟完成为规划目标；小型代码修复通常以 `10～30` 分钟完成为规划目标。时间目标不是验收标准，也不得通过跳过必要验证来强行满足。
- 完整 Spec、首次独立验收、共享基础设施变更或明确需要完整回归的任务可以超过上述目标，但报告中必须说明验证升级依据。

### 验证升级条件

只有出现以下至少一项时，才从定向验证升级到全量静态检查、全量测试、构建或完整 Browser E2E：

- 改动跨越多个共享模块且影响无法可靠限定；
- 修改认证、会话、全局路由、数据库迁移、构建配置、测试运行器或运行时基础设施；
- 定向测试发现新的连锁失败；
- 上一次相关全量结果发生在重大改动之前，已经失去代表性；
- Spec、任务交接或用户明确要求；
- 实施或验收 Agent 提供具体证据说明更大范围验证是形成可靠结论所必需的。

升级时只增加与风险匹配的层级，不自动把所有可用命令全部运行一遍。

## 分层本地验证策略

### 层级 1：实施过程定向反馈

- 开发过程中只运行直接覆盖当前改动的单元、组件、接口或 Browser E2E；
- 优先使用能够在修复前失败、修复后通过的最小测试集合；
- 不要求每次修改后运行全仓测试、构建或完整 Browser E2E。

### 层级 2：初次实施交付

- 初次实施完成时运行适用的格式、Lint、类型检查、单元/集成测试和构建；
- Browser E2E 只运行当前 Spec、改动模块及高风险相邻行为的相关场景；
- 初次实施阶段默认不运行完整 Browser E2E，除非 Spec 明确要求，或改动涉及测试基础设施、框架、全局路由、认证会话等无法可靠限定影响的范围。

### 层级 3：初次独立验收

- 初次独立验收必须独立检查差异、运行关键验收项，并运行一次完整 Browser E2E；
- 这一次完整 Browser E2E 是该轮 Spec 的完整浏览器回归，不要求实施 Agent 预先重复同一套完整矩阵；
- 验收 Agent 可以复用已安装依赖和项目现有测试设施，但不得直接采信实施结果。

### 层级 4：返工与复验

- 小范围返工实施只运行历史失败用例、直接受影响回归和必要静态检查；
- 小范围独立复验只独立复现历史失败、验证修复并检查受影响相邻行为；
- 默认不在返工 Agent 和复验 Agent 中再次运行完整 Browser E2E；
- 出现以下任一情况时升级为完整 Browser E2E：
  - 返工修改跨越多个页面、模块或前后端边界；
  - 修改共享布局、路由、认证、会话、媒体、测试运行器或其他基础设施，且影响无法可靠限定；
  - 定向测试发现新的连锁失败；
  - 上一次完整 Browser E2E 发生在重大改动之前，已经不能代表当前工作区；
  - 验收 Agent 提供证据说明完整回归是形成可靠结论所必需的。

### 浏览器分层

- 普通业务回归以 Chromium 为主要环境；
- Firefox 和 WebKit 聚焦浏览器差异明显的布局、滚动、历史导航、弹框、焦点、文件上传、媒体和 Cookie 场景；
- 具体 Spec 可以基于风险要求三浏览器覆盖更多场景；
- 不得仅为减少时间而省略 Spec 明确要求的浏览器行为。

### 报告要求

- 交接中必须声明本轮验证层级、必跑测试和是否要求完整 Browser E2E；
- 报告必须分别列出定向测试、相关回归、完整回归和未运行项；
- 按分层策略未运行的检查记录为“未运行”，并说明依据，不得记为“通过”；
- 发现实际影响超出预期时必须提高验证层级，不得固守原定最小范围。

## 实施阶段

实施 Agent 至少应：

- 运行直接覆盖改动的测试；
- 运行适用的类型检查、静态检查或构建；
- 检查受影响的异常路径和边界条件；
- 对新增或修复的行为补充适当的自动化测试；
- 记录命令、结果和未运行项原因。

实施 Agent 应遵守上述分层策略，不得在交接没有要求、风险没有升级的情况下机械运行完整 Browser E2E。

## 验收阶段

验收 Agent 应：

- 不依赖实施 Agent 的结论，独立运行关键检查；
- 按 Spec 验收项逐项记录证据；
- 验证失败路径、权限、数据边界及相关回归；
- 区分环境问题、测试问题、实现问题和 Spec 问题；
- 不通过修改代码让测试“变绿”。

初次独立验收与返工复验使用不同层级：前者运行一次完整 Browser E2E，后者默认验证历史失败项和受影响回归。

## 失败处理

- 不得隐藏、删除或忽略失败测试。
- 已知与当前任务无关的失败也要记录，并说明判断依据。
- 若测试环境缺失，报告具体缺失项和恢复验证所需条件。
- 不得在没有证据时将偶发失败标记为无关。

## 验收证据

可接受的证据包括：

- 测试或构建命令及退出结果；
- 可复现的操作步骤和观察结果；
- 相关日志、截图或输出文件；
- 精确的文件位置和代码检查结论。

敏感信息不得写入验收证据。

## 常规 CI 范围

- `ci.yml` 不安装浏览器，也不运行 `pnpm test:e2e`；
- 常规 CI 仍通过根级 `pnpm lint` 和 `pnpm typecheck` 检查 `e2e/` 源码；
- Browser E2E 由具体 Spec 的实施和独立验收在本地按风险运行，不得因移出 CI 而省略 Spec 明确要求的浏览器验收；
- 未来如需发布前浏览器门禁，应通过新的已确认决策建立独立手动工作流或发布前 Smoke E2E，不直接恢复到常规 CI。

## E2E 测试版本控制

- `e2e/` 中的 Playwright 配置、测试脚本、测试辅助代码和必要的非敏感测试夹具属于可复用项目源码，必须纳入 Git。
- SPEC 要求新增或调整端到端场景时，对应 E2E 测试脚本必须随业务实现一同交付，不得只保存在临时验收目录。
- `playwright-report/`、`test-results/`、`blob-report/`、截图、录像、追踪文件和其他单次运行产物不纳入 Git；需要长期保存的验收证据应整理为不含敏感信息的文本记录。

## 临时测试副本与自动清理

- 只有在验证干净安装、隔离构建或其他必须使用独立工作区的场景中，才创建项目临时副本。
- 临时副本必须创建在仓库根目录 `test/` 下的任务专属子目录中，例如 `test/spec-001-acceptance-round-1/`；不得创建到 `%TEMP%`、`C:\Users\...\AppData\Local\Temp` 或仓库外的其他位置。
- 创建副本时必须排除根目录 `test/` 本身，防止递归复制；还应按测试目标排除 `.git/`、`node_modules/`、构建产物、测试产物、真实环境文件、本地数据和媒体目录。
- 创建、使用和删除前必须解析并核对绝对路径，确认目标严格位于当前仓库根目录的 `test/` 内。禁止对仓库根目录、`test/` 以外路径或未解析变量执行递归删除。
- 测试脚本或 Agent 必须使用等价于 `try/finally` 的清理流程：无论测试通过、失败或中途出现可处理异常，都自动删除本轮创建的临时验收脚本和其他一次性测试文件。
- 任何 `node_modules/` 均不属于自动清理范围。已存在或本轮生成的 `node_modules/` 可以保留以避免后续重复安装；未经用户明确要求，不得为了清理临时验收文件而删除它。
- 如果任务专属子目录中仍保留 `node_modules/`，可以保留承载这些依赖目录所需的父目录；除此之外的一次性脚本、项目副本文件和测试产物仍须清理。
- 只有在没有需要保留的 `node_modules/` 且任务专属子目录已经清空时，才删除该子目录；根目录 `test/` 已为空时可以一并删除，不得删除其他任务创建的子目录。
- 若回合或进程被强制中断而无法执行自动清理，协调开发 Agent 恢复时必须先确认没有相关进程正在使用临时文件，再按上述规则清理；不得同时删除保留的 `node_modules/`。
- 实施报告或验收报告必须记录临时副本路径、用途、一次性文件清理结果，以及所有保留的 `node_modules/` 路径。临时副本和其中生成的文件不得作为长期验收证据；需要保留的证据应整理为不含敏感信息的文本记录。
