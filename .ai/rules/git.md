# Git 操作规则

## 默认权限

除非用户在当前任务中明确授权：

- 不创建或切换分支；
- 不暂存文件；
- 不创建提交；
- 不推送远端；
- 不创建、合并或关闭 Pull Request；
- 不改写历史；
- 不创建或删除标签。

完成任务不以提交代码为前提。

## 推荐交付流程

1. 实施 Agent 完成开发和自测。
2. 独立验收 Agent 完成本地验收。
3. 协调开发 Agent 向用户汇报改动范围、测试结果和已知风险。
4. 用户明确确认验收完成后，协调开发 Agent 将 Spec 标记为 `Accepted` 并提供提交信息。
5. 默认由用户自行创建提交并推送代码。
6. 推送后由 GitHub Actions 自动运行 CI；CI 不属于 Spec 验收项，其结果不改变已经确认完成的 Spec 状态。
7. 提交或 CI 出错时，用户将错误信息交回协调开发 Agent，由协调开发 Agent 组织实施和独立复验，直至错误修复。

如果用户临时要求 Agent 代为提交或推送，仍需针对当前任务、仓库和目标分支明确授权；该授权不自动扩展为后续任务的长期授权。

## 提交信息语言

- 提交标题必须使用 Conventional Commits 类型前缀，例如 `feat:`、`fix:`、`docs:`、`refactor:`、`test:`、`chore:`、`ci:` 或 `build:`。
- 类型前缀使用约定的英文关键字；冒号后的标题描述以及提交正文统一使用中文。
- 标题应简洁说明本次提交带来的主要变化，正文按需列出重要实现、测试或治理变更。
- 除类型前缀外，不得将中文标题替换为纯英文提交信息。

## 允许的只读检查

Agent 可以按任务需要执行：

- 查看工作区状态；
- 查看差异和提交历史；
- 查看当前分支和远端配置；
- 比较文件或提交；
- 定位已有改动来源。

只读检查也不得暴露凭据或无关敏感信息。

## 获得授权后

- 明确仓库、分支、文件范围和目标远端；
- 提交只包含本任务相关改动；
- 不混入用户或其他 Agent 的无关改动；
- 提交信息使用 Conventional Commits 类型前缀和中文描述，并准确说明行为变化；
- 推送前报告测试状态和已知风险；
- 禁止使用强制推送，除非用户对确切分支明确授权。

## 禁止的默认恢复方式

不得使用可能丢失工作区内容的命令来处理未知改动，包括硬重置、强制检出覆盖和无确认清理。需要恢复或删除内容时，先解析精确目标并获得相应授权。
